# PRD · HRAgent Harness
## 一个可观测、可评测的受控 Agent 运行时

| 项目 | 内容 |
|---|---|
| 项目代号 | **HRAH**（HRAgent Harness） |
| 一句话定位 | 一个自己写的 Agent 运行时 + 一套给它打分的评测体系，用 HR 招聘场景验证 |
| 文档版本 | v0.1（草稿） |
| 状态 | 开发中 · M2 上下文管理与会话状态机已实现 |
| 日期 | 2026-10-05 |
| 性质声明 | **个人独立项目**，非公司产品，未上生产，无真实企业用户与流量 |

---

## 0. 文档说明

### 0.1 这份 PRD 定义什么

本 PRD 定义 **HRAH 是什么、为谁做、解决什么问题、包含哪些能力、怎么算做对了**。

它不是一份"HR 系统"的 PRD。HR 招聘（JD 生成、简历筛选、面试安排、邮件通知）在本项目中是**验证场景**，不是产品本体。产品本体是让这些任务能被稳定、可控、可追溯地完成的**运行时**，以及证明它确实做到位的**评测体系**。

### 0.2 为什么这样定位

企业里落地 AI Agent 时，真正的难点从来不是"接一个大模型"，而是四件没人愿意做的事：

| 难点 | 具体表现 |
|---|---|
| **不可控** | 模型想调什么工具就调什么，动作空间没有边界 |
| **不可观测** | 结果错了，说不清是哪一步错的，只能重跑一遍碰运气 |
| **不可评测** | "感觉还行"就算验收，改一版 prompt 不知道是变好还是变坏 |
| **上下文失控** | 聊几轮就爆 token，或者关键信息被历史挤掉了 |

本项目的目标就是把这四件事**做成显式设计**，并在一个真实场景里跑出可验证的数据。

### 0.3 参考与致谢

本项目为个人独立设计与实现。设计思路参考了：

- 一门 AI 产品落地课程提供的 HR Agent 案例材料（产品文档与参考实现），用于理解业务场景与评测框架的组织方式
- Dify 等开源/商用编排平台的公开设计
- 社区关于 Agent 评测、上下文工程的公开实践

**本项目的代码、评测集、架构决策均为独立编写，未复制课程提供的源码。** 课程参考实现在本项目中仅作为**对照基线**存在（见第 10 节）。

## 1. 产品概述

### 1.1 一句话说清

> HRAH 是一个让 AI Agent 干活"有边界、看得见、测得准"的运行时：用户（HR）用一句话下达任务，系统在固定的动作空间内决定该调什么工具、缺什么信息就追问、涉及高风险动作先停下等人确认，并且每一次决策都留下可回放的 Trace；配套一套评测体系，用固定用例集反复跑，量化它到底靠不靠谱。

### 1.2 解决什么问题

| # | 问题 | 现状做法 | HRAH 的做法 |
|---|---|---|---|
| P1 | Agent 动作无边界 | 提示词里写一句"你可以用这些工具"，靠模型自觉 | 工具注册表 + 固定动作空间，注册表外的调用一律拒绝 |
| P2 | 出错定位不了 | 只看最终输出，中间过程黑盒 | 结构化 Trace：意图 → 规划 → 每次工具调用 → 门控 → 响应，全链路可回放 |
| P3 | 改一版不知道好坏 | 人工抽几条试试 | 固定用例集 + 规则/LLM 双裁判 + 多次重复运行 + baseline 回归 |
| P4 | 上下文失控 | 历史全量塞进去，爆了就截断 | 显式 token 预算分配 + 分层裁剪与摘要策略 |
| P5 | 多轮任务没有状态 | 每轮当成新对话，流程接不起来 | 显式会话状态机，状态驱动行为 |
| P6 | 高风险动作没人管 | 直接执行，错了不可逆 | 风险分级 + 人工确认门控，门控 100% 触发 |

### 1.3 产品价值（对三类对象）

| 对象 | 价值 |
|---|---|
| **HR 使用者** | 一句话下达招聘任务，缺信息系统会追问，发邮件/安排面试一定会先问过人 |
| **开发者（我自己）** | 得到一个能讲清每一个设计取舍的 Agent 运行时，而不是一个调不通的黑盒 |
| **评审/面试官** | 能看到完整的设计文档、可运行代码、真实评测数据与失败归因，而非一段描述 |

### 1.4 成功标准（本项目自设目标，非行业标准）

| 维度 | 目标 |
|---|---|
| 功能 | 4 个 HR 任务端到端跑通，引擎与场景解耦 |
| 可控性 | 工具调用 100% 落在注册表内；高风险动作门控触发率 100% |
| 可观测 | 每次运行产出完整 Trace，Trace 完整率 100%，可单条回放 |
| 可评测 | 24 条用例 × 3 轮，输出通过率、稳定性、失败模式分布 |
| 可复现 | 换一台机器、换一个模型，同一套命令能跑出同样的报告 |

## 2. 产品边界

### 2.1 范围内

| 层级 | 模块 |
|---|---|
| 场景层 | JD 生成、简历筛选、面试安排、邮件通知（4 个任务） |
| 引擎层 | 工具注册表、受控规划器、上下文管理器、会话状态机、Trace、人工门控 |
| 评测层 | 用例集、裁判（规则 + LLM）、多次重复运行、baseline 回归、报告生成 |
| 对照层 | Dify 工作流实现同一批任务，作为基线对照 |
| 呈现 | 一个轻量看板（评测报告 + Trace 回放），不追求视觉 |

### 2.2 明确不做（P0 声明，避免范围膨胀）

- ❌ **不做完整 HR SaaS**：没有登录鉴权、没有多租户、没有角色权限体系、没有组织架构
- ❌ **不做真实邮件发送**：邮件工具为 mock，落草稿文件即可，不接真实 SMTP
- ❌ **不做 RAG 深度优化**：知识检索用最简实现（本地向量库或关键词），重点不在检索算法
- ❌ **不做前端工程**：一个轻量看板足够，不写 Vue/React 全家桶
- ❌ **不做模型训练/微调**：只用现成 LLM API
- ❌ **不做线上部署与真实用户试用**：本地可运行即为完成标准

> 说明：这些"不做"是**主动的范围裁剪**，不是能力缺失。裁剪原则是——凡是不能证明"Agent 运行时能力"的工作，一律砍掉。

### 2.3 三条设计底线

1. **AI 不替人做最终决定**：高风险动作必须经人工确认，确认前只出草稿。
2. **一切行为可追溯**：任何一次运行都能还原完整决策链路。
3. **一切结论有数据**：不出现"效果不错"这类无法验证的表述，所有结论来自评测报告。

## 4. 系统架构

### 4.1 三层结构

```
┌─────────────────────────────────────────────┐
│  场景层  HR 任务：JD / 简历 / 面试 / 邮件      │
└─────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────┐
│  引擎层  harness/                            │
│  工具注册表 · 受控规划器 · 上下文管理器        │
│  会话状态机 · Trace · 人工门控                │
└─────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────┐
│  评测层  用例集 · 双裁判 · 重复运行 · 回归     │
└─────────────────────────────────────────────┘
```

### 4.2 引擎层模块清单

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `tool_registry.py` | 声明可用工具，定义参数契约与风险等级 | 注册表外调用一律拒绝；按意图只注入相关工具定义 |
| `planner.py` | 决定下一步动作（调工具 / 追问 / 请求确认 / 结束） | 受控 ReAct：动作空间固定为 4 种，不允许自由发挥 |
| `context_manager.py` | 组装每次请求的上下文，控制 token 预算 | 分区预算 + 分层裁剪 + 早期历史摘要 |
| `session_state.py` | 维护会话状态与槽位（已收集的信息） | 显式状态机，状态驱动行为 |
| `tracer.py` | 记录每次运行的完整链路 | trace_id + span 树，含输入/输出/耗时/token/状态 |
| `gate.py` | 高风险动作的人工确认门控 | 风险分级，高风险必拦 |

### 4.3 双轨设计（自研 harness vs Dify）

同一批 HR 任务有两条实现路径，跑同一套评测集：

| | 自研 harness | Dify 工作流（云端版） |
|---|---|---|
| 定位 | 主轨道，展示引擎能力 | 对照组，现成编排平台基线 |
| 实现 | Python，约 20 文件 | 云端可视化编排 + API 调用 |
| 评测 | 同一套 24 条用例、同一套裁判 | 同左 |

对照结论将沉淀为一篇 ADR：《什么情况下必须自研 harness，什么情况下用 Dify 就够了》。

## 5. 功能需求

### 5.1 工具注册表（FR-001 组）

工具是 Agent 唯一被允许执行的动作来源。

| 工具名 | 说明 | 风险等级 | 需人工确认 |
|---|---|:---:|:---:|
| `generate_jd` | 生成岗位 JD 初稿 | 低 | 否 |
| `generate_rubric` | 生成简历评分标准 | 低 | 否 |
| `screen_resume` | 结合 JD 与评分标准给简历打分 | 低 | 否 |
| `generate_interview_plan` | 生成结构化面试方案 | 低 | 否 |
| `search_knowledge` | 检索制度/知识库 | 低 | 否 |
| `get_candidate` | 查询候选人信息 | 低 | 否 |
| `draft_email` | 生成邮件草稿（不发送） | 中 | 否 |
| `schedule_interview` | 安排面试 | 高 | **是** |
| `send_email` | 发送邮件 | 高 | **是** |

每个工具声明包含：名称、描述、参数 JSON Schema、风险等级、返回结构、失败语义。

### 5.2 受控规划器（FR-002 组）

规划器的动作空间**固定为 4 种**，不允许其他输出：

| 动作 | 含义 |
|---|---|
| `CALL_TOOL` | 调用注册表中的某个工具 |
| `ASK_USER` | 向用户追问缺失信息 |
| `REQUEST_CONFIRM` | 请求人工确认高风险动作 |
| `FINISH` | 结束并给出最终回应 |

### 5.3 条件缺口三分类（FR-003 组）

当任务无法直接执行时，判断缺口类型并采取不同策略：

| 类型 | 判断依据 | 系统行为 |
|---|---|---|
| `MISSING_INFO` | 缺用户输入（如没说岗位、没说候选人） | 追问，一次只问最关键的 1~2 项 |
| `MISSING_PREREQUISITE` | 缺前置产物（如没 JD 就要筛简历） | 说明缺什么，引导先完成前置 |
| `MISSING_CONFIRMATION` | 信息齐全但动作高风险 | 出草稿 + 请求确认 |

### 5.4 上下文管理（FR-004 组）

**Token 预算分配（占模型窗口比例）**

| 分区 | 预算 | 裁剪策略 |
|---|:---:|---|
| 系统提示 | 15% | 固定，不裁剪 |
| 工具定义 | 20% | 只注入与当前意图相关的 top-k 工具 |
| 检索片段 | 25% | 按相关度截断，标注来源 |
| 对话历史 | 30% | 近 3 轮保留原文，更早部分压缩为摘要 |
| 生成预留 | 10% | 不可占用 |

超出预算时必须记录一次 `context_truncated` 事件到 Trace。

### 5.5 会话状态机（FR-005 组）

```
IDLE ──> INTENT_RESOLVED ──> PLANNING ──> EXECUTING ──> DONE
              │                  │             │
              │                  ↓             ├──> FAILED
              │          AWAITING_INPUT        │
              │          AWAITING_CONFIRM      └──> ESCALATED
              └──> CLARIFYING
```

### 5.6 Trace（FR-006 组）

- 每次运行生成唯一 `trace_id`
- Span 类型：`intent` / `plan` / `tool_call` / `gate` / `respond`
- 每个 span 记录：父 span、类型、输入摘要、输出摘要、耗时、token 数、状态
- 支持按 trace_id 单条回放，输出人类可读的时间线

### 5.7 评测体系（FR-007 组）

**用例集（24 条，分 4 类）**

| 类别 | 条数 | 考察点 |
|---|:---:|---|
| A · 意图识别 | 6 | 能不能听懂要办什么事 |
| B · 缺口处理 | 6 | 缺信息/缺前置/缺确认的分类是否正确 |
| C · 工具调用与门控 | 6 | 参数是否合法、高风险是否拦住 |
| D · 内容质量 | 6 | 产出内容是否可用 |

**双裁判**

| 裁判 | 适用 | 特点 |
|---|---|---|
| 规则裁判 | A/B/C 类 | 确定性判定，可复现 |
| LLM 裁判 | D 类 | 评分 + 理由，重复 3 次取多数 |

**运行方式**：每条用例重复 3 轮，计算一致率（稳定性）；支持 `--baseline` 与历史版本对比。

## 6. 核心流程

### 6.1 Agent 执行主链路

```
1. 用户输入
2. 意图识别 ──────────> 不确定则进入 CLARIFYING
3. 收集槽位信息
4. 缺口判断 ── 缺信息 ──> ASK_USER，回到 1
              └─ 缺前置 ──> 提示前置，结束本轮
5. 规划：选工具（仅注册表内）
6. 风险判定 ── 高风险 ──> REQUEST_CONFIRM（出草稿）
                          └─ 用户拒绝 ──> 取消
                          └─ 用户同意 ──> 继续
7. 执行工具，结果写入 Trace
8. 结果整合，回到 4 直到无缺口
9. FINISH，给出最终回应
```

### 6.2 需要覆盖的异常场景

| 场景 | 期望行为 |
|---|---|
| 用户要求调用注册表外的能力 | 明确说明不支持，不臆造工具 |
| 工具执行失败 | 记录失败 span，重试一次，仍失败则上报原因 |
| 用户拒绝高风险确认 | 取消动作，保留草稿，不残留副作用 |
| 上下文超预算 | 触发裁剪并记录事件，不静默丢信息 |
| 模型输出非法动作 | 拒绝执行，记为规划失败并重试一次 |

## 7. 需求描述（EARS 格式）

**通用约束（Ubiquitous）**

- FR-001：系统应当只允许调用工具注册表中声明的工具。
- FR-002：系统应当为每次运行生成唯一 `trace_id`，并保证链路完整。
- FR-003：系统应当保证高风险动作在执行前必须经过人工确认。

**事件驱动（Event-driven）**

- FR-004：当用户提交一条新指令时，系统应当先进行意图识别，并在置信度不足时进入澄清状态。
- FR-005：当识别出任务缺少必要输入时，系统应当以 `MISSING_INFO` 处理，并一次只追问最关键的 1~2 项。
- FR-006：当识别出任务缺少前置产物时，系统应当以 `MISSING_PREREQUISITE` 处理，并说明需要先完成什么。
- FR-007：当规划结果为高风险工具调用时，系统应当生成草稿并请求人工确认。
- FR-008：当用户拒绝确认时，系统应当取消该动作且不产生任何副作用。
- FR-009：当工具调用失败时，系统应当记录失败 span，重试一次，仍失败则向用户说明原因。
- FR-010：当模型输出不在允许动作空间内时，系统应当拒绝执行并记为规划失败。

**状态驱动（State-driven）**

- FR-011：当会话处于 `AWAITING_CONFIRMATION` 状态时，系统应当暂停执行，仅等待确认或取消。
- FR-012：当会话处于 `AWAITING_INPUT` 状态时，系统应当保存已收集的槽位信息，不被新输入清空。

**异常（Unwanted）**

- FR-013：如果上下文组装超出 token 预算，则系统应当按分区策略裁剪，并在 Trace 中记录 `context_truncated` 事件。
- FR-014：如果用户请求的能力不在注册表中，则系统应当明确告知不支持，不得臆造工具或编造结果。
- FR-015：如果评测运行中出现裁判不可用，则系统应当标记该条用例为"未判定"，不得计入通过率。

**可选（Optional）**

- FR-016：在配置开启 Dify 对照模式时，系统应当用同一套用例集调用 Dify 工作流并输出对照报告。

## 8. 数据指标与成功度量

### 8.1 北极星指标

**可控完成率** = 在固定用例集上，「任务完成 且 全程动作合规」的比例。

选它的理由：单纯的任务完成率会掩盖"蒙对了但过程违规"，而 Agent 落地的风险恰恰来自过程不可控。

### 8.2 指标表

| 指标 | 定义 | 目标值 | 备注 |
|---|---|:---:|---|
| 意图识别准确率 | A 类用例意图判定正确比例 | ≥ 90% | 24 条固定用例集 |
| 契约通过率 | 工具调用参数合法、且在注册表内 | 100% | 硬指标，不允许例外 |
| 门控触发率 | 高风险动作触发确认的比例 | 100% | 硬指标 |
| 门控误伤率 | 低风险动作被误拦的比例 | ≤ 10% | 避免过度打扰 |
| 稳定性 | 同一用例 3 轮结果一致率 | ≥ 90% | |
| Trace 完整率 | 能完整回放的运行占比 | 100% | 硬指标 |
| 可控完成率 | 完成且全程合规 | ≥ 80% | 北极星 |
| 上下文超预算率 | 触发裁剪的运行占比 | ≤ 10% | |
| 失败可定位率 | 失败用例能归因到具体模式的比例 | ≥ 90% | 对照 Dify 的关键差异项 |

> ⚠️ 以上目标值为**本项目自设目标**，用于驱动迭代，不是行业验收标准，也不代表线上表现。

## 10. 双轨对照设计

### 10.1 为什么要对照

"为什么不用现成的编排平台"是 Agent 产品岗的高频问题。空口回答没有说服力，用同一把尺子量两条路才有。

### 10.2 对照维度

| 维度 | 说明 |
|---|---|
| 用例通过率 | 同一批 24 条用例 |
| **失败可定位率** | 失败后能否说清错在哪一步 —— 预期为最大差异项 |
| 可复现性 | 重复 3 轮结果是否一致 |
| 上下文可控性 | 长对话下是否失控 |
| 改动成本 | 修一个问题需要改多少东西 |

### 10.3 预期结论（待数据验证，不预设）

- Dify 在**标准流程**上更快落地
- 自研 harness 在**失败定位、上下文控制、状态管理**上更可控
- 结论写入 ADR-00X：《编排平台选型：什么时候必须自研》

## 11. 风险与 Pre-Mortem

| 风险 | 可能后果 | 缓解措施 |
|---|---|---|
| 用例由我自己编写，可能为"通过"而设计 | 数据不可信，被追问时站不住 | 用例设计规则外置、公开全部用例与失败样本、保留原始失败记录 |
| LLM 裁判本身不稳定 | 评分波动 | 裁判重复 3 次取多数，与规则裁判交叉验证 |
| 没有真实用户，结论缺乏外部效度 | 被质疑"自嗨" | 明确声明为离线固定用例集结果，不做线上外推 |
| 范围膨胀，做成半个 HR 系统 | 时间耗尽，重点失焦 | 严格守住 2.2 的"不做"清单 |
| 时间不足 | 半成品 | MVP 优先级：引擎核心 + 评测 > Dify 对照 > 看板 |
