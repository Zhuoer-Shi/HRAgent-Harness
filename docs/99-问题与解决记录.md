## BUG-001 · 提示语污染了工具入参

- **日期**：2026-10-05
- **发现方式**：自己发现（跑 demo 场景 5 时看到输出异常）
- **现象**：
  用户说"帮我查一下年假制度"，工具收到的 query 却是：
  ```
  '帮我查一下年假制度\n请只输出一个 JSON 对象。'
  ```
  把写给模型看的提示语尾巴一起传进去了。功能能跑通，但数据在悄悄变脏。
- **定位过程**：
  1. 确认输出异常 → 工具入参不对
  2. 看 `harness/llm.py` 的 `_decide()`，发现 `search_knowledge` 分支写的是 `{"query": u}`
  3. 追 `u` 的来源：`_route()` 从 `【用户最新输入】` 之后截取全部内容，包含 planner 拼的尾句
- **原因**：
  planner 组装 prompt 时在末尾追加了 `请只输出一个 JSON 对象。`，
  而 Stub 的入参解析直接整段截取，没有剥离提示语。
- **修复**：
  ```python
  # harness/llm.py  _decide()
  u = (user or "").split("请只输出一个 JSON 对象")[0].strip()
  ```
- **教训**：
  **模型看到的文本 ≠ 用户说的话。** 两者必须在解析层显式分离。
  这类问题不会报错、不会崩溃，只会让数据慢慢变脏——是最容易被忽略的一类 bug。
  面试可讲："我调试时发现提示语污染了工具入参，功能是对的，但传进去的数据是脏的。"

## BUG-002 · 共享 session 导致后续场景被短路

- **日期**：2026-10-05
- **发现方式**：协助调试发现（AI 跑 demo 时发现所有场景结果相同）
- **现象**：
  4 个场景全部返回 `done`，场景 2/3/4 应该分别是追问、待确认，却都被判成"已完成"。
- **定位过程**：
  1. 观察：只有第一个场景是真的执行了工具
  2. 追 `runner.run()` → `session.observations` 是实例级共享的
  3. Stub 的策略是"只要看到 `【已执行步骤与结果】` 就 FINISH"
  4. 场景 1 执行后 observations 非空 → 场景 2/3/4 一进来就被 FINISH
- **原因**：
  demo 复用同一个 `AgentRunner`（同一个 session），上一轮的 observations 串到了下一轮。
- **修复**：
  ```python
  # demo.py：每个场景独立会话
  for i, text in enumerate(SCENARIOS, 1):
      runner = AgentRunner(llm, registry, max_steps=6, auto_confirm=False)
  ```
- **教训**：
  **评测与演示必须保证用例之间状态隔离**，否则指标全部失真。
  这条后来会成为评测框架的一条硬约束：每条用例独立 runner。

## BUG-003 · 关键词歧义导致意图误判

- **日期**：2026-10-05
- **发现方式**：协助调试发现（AI 跑 demo 时发现场景 3/4 路由错误）
- **现象**：
  - "给张三安排明天下午面试" → 没匹配上，走了兜底 FINISH
  - "发邮件通知候选人面试时间" → 被判成"安排面试"（因为含"面试时间"）
- **定位过程**：
  1. 看 `StubLLM._decide()` 的分支顺序
  2. `schedule_interview` 的关键词含"面试时间"，抢在邮件分支前面命中
  3. "安排明天下午面试"不含连续的"安排面试"，所以匹配失败
- **原因**：
  关键词设计太具体（要连续匹配）且分支顺序不合理。
- **修复**：
  ```python
  # 1. 邮件分支前置（含"邮件"优先判定）
  # 2. 安排面试改为组合判断，不再要求连续字符串
  if "面试" in u and any(k in u for k in ("安排", "约", "预约", "定", "排期")):
  ```
- **教训**：
  **意图路由的分支顺序就是隐式优先级**，必须显式设计并写注释说明为什么这么排。
  真实场景里这应该用意图分类器 + 评测集来验证，而不是堆关键词。

## BUG-004 · 关键词间隔表达导致工具漏选（M2 上下文管理阶段暴露）

- **日期**：2026-10-05
- **发现方式**：自己发现（跑 `demo.py --context` 时看到备注"无工具命中关键词"）
- **现象**：
  M2 上线后，场景 3「给张三安排明天下午面试」的上下文账本打出一条备注：
  ```
  备注: 无工具命中关键词，仅注入得分最高的 1 个（模型应 FINISH 说明不支持）
  注入工具: ['draft_email', 'schedule_interview', 'send_email']
  ```
  明明是要安排面试，`schedule_interview` 却是靠"高风险工具保护规则"兜底进去的，
  不是靠意图匹配进去的。**功能没坏，但意图筛选这一段实际是失效的。**
- **定位过程**：
  1. 看账本备注 → 一个工具都没命中
  2. 查 `tools/hr_tools.py` 里 `schedule_interview` 的 keywords：
     `["安排面试", "约面试", "面试时间", "预约"]`
  3. 用户输入是「给张三安排明天下午面试」——"安排"和"面试"中间隔了 5 个字，
     四个关键词**没有一个能连续命中**
  4. 对比：Stub 之所以还能正确调工具，是因为 BUG-003 修过组合判断，
     **兜底逻辑掩盖了筛选逻辑的缺陷**
- **原因**：
  字面关键词匹配要求连续子串，对"动词 + 插入语 + 名词"这种自然语言表达天然不兼容。
- **修复**：
  ```python
  # tools/hr_tools.py
  schedule_interview:      keywords=[..., "面试"]     # 补一个宽口径词
  generate_interview_plan: keywords=[..., "方案", "问题"]  # 同时补特征词，避免被"面试"抢走
  ```
  靠"命中数量打分"来区分：「安排…面试」只有 schedule 命中 1 次；
  「生成面试方案」plan 命中 2 次（面试方案 + 方案）→ plan 胜出。
- **教训（这条很值钱）**：
  1. **兜底逻辑会掩盖主逻辑的缺陷**。如果不是 M2 把"注入了哪些工具、为什么"
     显式打进账本，这个失效会一直躲在"反正功能是对的"后面。
     → 这就是**可观测性的直接收益**：不是等它炸，而是让它主动告诉你哪里在退化。
  2. 关键词匹配只是过渡方案。M4 接真模型时应换成 embedding 相似度，
     并用评测集的"意图识别准确率"来量化换与不换的差别。
  3. 面试可讲："我做完上下文预算之后，账本里一条备注暴露了意图筛选其实是失效的——
     这个 bug 之前一直被兜底逻辑盖住了。"

## BUG-005 · 关键词过宽导致误注入无关工具（与 BUG-004 同根因的另一面）

- **日期**：2026-10-05
- **发现方式**：协助定位（用户复查 `demo.py --context` 账本后问"这个结果对吗"，核对时发现）
- **现象**：
  场景 4「发邮件通知候选人面试时间」注入了 3 个工具：
  ```
  注入工具: ['send_email', 'schedule_interview', 'get_candidate']
  ```
  其中 `get_candidate`（查候选人状态）跟"发面试通知"这件事毫无关系，属于误注入。
- **定位过程**：
  1. 逐个核对被注入工具的关键词命中来源
  2. `get_candidate` 的 keywords 含「候选人」——而用户句子里正好有"候选人"三个字
  3. 同理 `schedule_interview` 的 keywords 含「面试」——"面试时间"也被它吃掉
- **原因**：
  BUG-004 修漏选时补进了「面试」「方案」「问题」这类宽口径词，
  代价是误命中率上升。**漏选和误选是同一根因的两面**：
  字面匹配没有语义，"候选人"既可能是查询意图，也可能只是句子的宾语。
- **修复**：
  本次只记录不改。当前靠"命中数量打分 + 排序"部分缓解，但根因在匹配方式本身。
  正式修复放在 M4：换成 embedding 相似度，并用评测指标量化换与不换的差别。
- **教训**：
  1. 关键词加宽会**同时**降低漏选、抬高误选。这两个指标必须一起看，
     只盯"有没有匹配上"，会把问题从一头推到另一头。
     → 所以 M3 评测集必须同时包含两类用例：「该选却没选」和「不该选却选了」。
  2. 这类问题只有把"注入了什么、为什么"显式打印才看得见——这是 M2 账本的第二次收益。

## 小坑 · Python 字符串里写中文引号导致 SyntaxError

- **日期**：2026-10-05
- **发现方式**：自己发现（跑 `scripts/context_benchmark.py` 报错）
- **现象**：
  ```
  File "scripts/context_benchmark.py", line 194
    "- 历史分区与"本轮执行结果"共享额度，执行结果优先（它是当前决策的直接依据）。",
  SyntaxError: invalid syntax. Perhaps you forgot a comma?
  ```
- **原因**：
  写 Markdown 报告内容时习惯性用了直引号 `"`，而外层的 Python 字符串也是 `"`，
  字符串被提前截断。
- **修复**：把内层引号去掉，改成 `历史分区与本轮执行结果共享额度`。
- **教训**：
  在 Python 源码里拼 Markdown 正文时，**内层一律不要出现 ASCII 直引号**；
  需要引号就用中文书名号或全角引号「」。

## 小坑 · 评测用例自己写错参数名，导致误报失败

- **日期**：2026-10-05
- **发现方式**：自己发现（首次跑 `scripts/run_evals.py`，C05 报错）
- **现象**：
  ```
  ❌ C05 工具必填参数缺失时，契约校验必须拦住
       - 参数齐全应通过｜validate 返回 ok=False，原因: 缺少必填参数: candidate
  ```
  名为「参数齐全应通过」的断言却失败了——看起来像是引擎的契约校验有 bug。
- **定位过程**：
  1. 看报错信息：缺的是 `candidate`
  2. 查 `tools/hr_tools.py` 里 `screen_resume` 的声明：`params={candidate, jd}`
  3. 我在用例里凭印象写的是 `resume_text`——**这个参数根本不存在**
- **原因**：**写测试用例时凭印象编参数名**，没有回看工具的真实声明。
  引擎没错，是**用例错了**。
- **修复**：改成真实参数 `{"candidate": ..., "jd": ...}`，并补一条「未声明参数应被拒绝」的断言
  （把这次踩的坑反过来变成一条正式用例）。
- **教训**：
  1. **看到用例失败，第一反应不能是「产品有 bug」，要先确认是产品错了还是用例错了。**
     我这次差点去改一个根本没问题的引擎。
  2. 断言的参数名必须来自工具声明，不能来自记忆。
  3. 顺手收获：把「未声明参数也应被拒绝」补进用例，等于用教训换了一条新覆盖。
