# 失败模式手册（Failure Mode Handbook）

> **定位**：把项目开发至今遇到的 **18 条失败 / 踩坑**，按根因归为四类，提炼出
> "怎么一眼判断是哪类、该谁修、怎么验证"。这是 `Trace 观测看板` 的配套——看板告诉你
> **失败在哪**，这份手册告诉你 **失败为什么、该谁负责**。
>
> **为什么值得写**：能把失败**归因**（而不是笼统说"有 bug"），是 Agent 产品经理
> 和普通 PM 的分水岭。它直接回答一个核心问题：**"你怎么定位一个失败？"**

---

## 0. 归因框架：四类失败

| 类别 | 定义 | 典型信号 | 该谁修 | 修复动作 |
|---|---|---|---|---|
| **引擎缺陷（Engine）** | 自己代码的逻辑 / 鲁棒性 bug | Stub 下也能复现；Trace 里 span 状态 `failed`；改代码就好 | 我（写引擎的人） | 改代码 + 补回归用例 |
| **模型缺陷（Model）** | 模型能力 / 内容质量不够 | 只有接真模型才复现；span 全 `ok` 但裁判判内容不过 | 换模型 / 调提示词 | 换端点或改 prompt |
| **度量评测缺陷（Judge）** | 用例 / 断言 / 基线写错了 | 引擎和模型其实都**做对了**，是度量判错了 | 我（写评测的人） | 改用例 / 修基线 |
| **环境外部缺陷（Env）** | 第三方平台 / 网络层的坑 | 只有联网 / 接第三方才触发；错误来自外部（403/400/SSL） | 加适配层 / 防御 | 加 UA、重试、改协议 |

**核心心法（先记住这一句）**：失败不是铁板一块。**先归因，再动手**——否则很容易去改一个根本没问题的引擎（本项目的"参数名小坑"就是活例子）。

## 2. 四类分述（每类看什么、怎么修）

### 2.1 引擎缺陷（8 条）—— 最该自己消灭的一类

这类是"自己的代码错了"。最危险的是**不报错的**（BUG-001 数据悄悄变脏、BUG-004 兜底掩盖主逻辑失效、BUG-006 数字悄悄失真）——它们不会崩，只会让结果"看起来对，其实错"。

**怎么发现**：靠**可观测性**。BUG-004 是上下文账本的一条备注暴露的，BUG-007 是 Trace 埋点挖出来的。**兜底逻辑会掩盖主逻辑的缺陷**，只有把"注入了什么、为什么、状态是什么"显式打出来，退化才会自己浮出来。

**最值钱的一条**（BUG-007）：参数名 `type` 遮蔽内置函数，**只在"先有另一个异常"时才二次崩溃**——Stub 永远触发不了，接真模型才暴露。教训：**兜底路径（span/日志/except）要当产品代码一样测**，不能假设它永远走不到。

### 2.2 模型缺陷（3 条）—— 不是你的错，但你要能证明

D03/D04/D05 全是 DeepSeek 内容质量不够，LLM 裁判打 0/0/20 分。关键：**span 全 `ok`、引擎零故障**，纯粹是模型写得浅。

**怎么证明是模型问题**：Trace 看板的失败归因里，"引擎层 span 零故障 + 失败全在裁判判定层"就是证据。这比口头说"是模型不行"可信得多。

**为什么不该硬改**：换模型 / 调 prompt 能解，但那不是"引擎能力"，硬改只会把评测指标刷好看、掩盖真实差距。

### 2.3 度量评测缺陷（5 条）—— 最容易误伤自己的"假失败"

这类是**引擎和模型其实都做对了，是度量判错了**。最典型：
- 参数名小坑：差点去改一个根本没问题的引擎。
- B05/C02/B04：真模型"先追问""没硬找关键词"这类**安全行为**，被过死的断言判成失败。

**心法**：**看到用例失败，第一反应不能是"产品有 bug"，要先确认是产品错了还是用例错了。** 把"假失败"当"真失败"修，是最浪费时间的一种内耗。

### 2.4 环境外部缺陷（2 条）—— 接第三方绕不开的坑

Cloudflare 按 UA 封 bot、Dify Agent 强制 streaming——都不是你的代码错，是**外部平台的约束**。这类只能靠"先看官方文档 + 加防御"。

**心法**：报 403 先怀疑 UA 再怀疑 key（`cfOrigin;dur=0` 告诉你"没到源站"）；接第三方 API 前先看应用类型差异，别套用直觉。

## 3. 关键洞察（4 条）

1. **先归因再修**：失败不是铁板一块，四类失败的四类修法完全不同。去改一个没问题的引擎，是最贵的错误。
2. **假失败 vs 真失败**：5 条"度量缺陷"其实是"假失败"——它们不是产品错，是度量错。能识别并剔除假失败，是评测能力成熟的标志。
3. **接真模型暴露了两类 Stub 覆盖不到的缺陷**：引擎层 BUG-007/008（只在网络/异常路径暴露）+ 模型层 D03~D05（内容质量）。这正是"为什么要接真模型、不能只靠 mock"的答案。
4. **兜底逻辑会掩盖主逻辑缺陷**：BUG-004 的意图筛选失效，一直被"高风险工具保护"兜底盖住，是账本备注把它暴露的。**可观测性不是等它炸，而是让它主动告诉你哪里在退化。**

## 4. 归因方法论：失败定位三步法

遇到一个失败，按这个顺序走，十秒内定位到"该谁修"：

```
第 1 步 · 看 Trace span 状态
   ├─ span 有 failed ──────────→ 引擎缺陷（改代码）
   └─ span 全 ok，但判失败 ────→ 往下
第 2 步 · 看失败发生在哪一层
   ├─ Stub 也能复现 ───────────→ 引擎缺陷 / 度量缺陷（改用例）
   ├─ 只有 live 复现 + 内容判不过 → 模型缺陷（换模型 / 调 prompt）
   └─ 只有联网 / 第三方触发 ────→ 环境缺陷（加防御）
第 3 步 · 定修复归属 + 验证
   └─ 改完必须能"被评测验证"——否则等于没修（对应项目的"没有验证方式的约束等于没有约束"）
```

## 5. 诚实声明

- 这 18 条失败来自**个人项目**（未上生产），是开发期真实踩的坑，不是线上事故数据。
- "引擎缺陷 8 条"不代表引擎质量差，恰恰相反——**绝大多数引擎缺陷是在 Stub 阶段或接真模型后主动暴露、主动修掉的**，没带病上线。
- 归因分类是本项目自设的分析框架，用于展示"失败可定位"能力，不是行业标准。
