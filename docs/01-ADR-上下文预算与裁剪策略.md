# ADR-001 · 上下文按分区预算管理，预算不足时按固定顺序裁剪

- **日期**：2026-10-05
- **状态**：已接受（M2 已实现）
- **关联**：PRD 5.4 / FR-004 / FR-005 / FR-006 / FR-013

---

## 1. 背景与问题

M1 的做法是"固定注入 top_k=5 个工具 + 历史对话全量拼接"。跑起来之后暴露两个问题：

1. **无关工具白吃 token**：写 JD 时把 `draft_email`、`generate_rubric` 也塞进去了
   （因为它们得分是 0，但 top_k 要求凑满 5 个）。实测每次注入 5~7 个工具，
   其中大多数与当前意图无关。
2. **历史无上限增长**：多轮对话后历史会无节制地把预算吃光，
   要么撑爆窗口，要么把工具定义挤掉——而工具定义被挤掉会导致模型臆造工具。

根因是：**上下文从未被当作一项有额度的资源来管理**，各段内容的增长互不相让。

## 2. 决策

### 2.1 分区预算

把一次规划调用的窗口切成 5 个区，每区独立额度：

| 分区 | 比例 | 裁剪策略 |
|---|:---:|---|
| system | 15% | 固定成本，**不裁剪**（超了只记备注） |
| tools | 20% | 只注入相关性得分 > 0 的工具；超预算按相关性从低到高裁剪 |
| retrieval | 25% | 按相关度顺序截断尾部片段 |
| history | 30% | 与"本轮执行结果"共享；先压缩早期轮次，仍超则丢弃最旧 |
| reserve | 10% | 不可占用 |

### 2.2 三条裁剪优先级（这条是本 ADR 的核心）

1. **执行结果优先于历史对话** —— 本轮已经调了什么工具、返回了什么，
   是当前决策的直接依据；早期客套话不是。
2. **高风险工具永不裁剪** —— `schedule_interview` / `send_email` 即使撑爆工具分区
   也必须注入。理由见第 3 节。
3. **宁可压缩，不要静默丢弃** —— 压缩会留下"这里曾有 N 条消息"的痕迹，
   静默丢弃不会。任何一次裁剪都必须写进账本与 Trace。

### 2.3 每次运行产出账本

`ContextPackage` 记录：各分区用量/上限、注入了哪些工具、裁掉了哪些、
历史压缩与丢弃条数、备注。账本进 Trace 的 `context.build` span，
也能在终端用 `python demo.py --context` 直接打印。

## 3. 关键取舍：为什么高风险工具不受预算约束

这是**安全优先于成本**的取舍。

工具定义被裁剪的直接后果不是"少一个功能"，而是**模型不知道这个能力存在，
于是自己编一个**。在 HR 场景里，一个被臆造出来的"发邮件"比多花 300 个 token
危险得多——前者可能产生真实的对外副作用。

代价：工具分区的实际占用可能超过 20%。这个代价被显式接受，
并在账本里以备注形式暴露，而不是悄悄吞掉。

## 4. 被否决的备选方案

| 方案 | 否决理由 |
|---|---|
| **全量注入 9 个工具，不筛选** | 工具定义随工具数线性膨胀；9 个还好，50 个就不可行。且无关工具会干扰模型选择 |
| **固定 top_k（M1 现状）** | top_k 是个拍脑袋的数：凑不满时会硬填无关工具，正好时能用的也可能被切掉 |
| **超预算时直接截断整个历史** | 静默丢信息，出问题无法归因。违反 PRD 三条设计底线里的"一切行为可追溯" |
| **每轮都用 LLM 做历史摘要** | 多一次模型调用 = 多一份延迟与成本，且摘要本身可能丢关键信息。当前规模下不划算；留到 M4 用数据决定 |
| **embedding 相似度选工具** | 效果更好，但要引入向量依赖与额外调用，破坏"零依赖可跑"的约束。留到 M4 接真模型时一并评估 |

## 5. 代价与已知局限

1. **token 估算是粗估**（CJK 按 1 字 ≈ 1 token，其余 4 字符 ≈ 1 token，刻意高估）。
   不追求与真实分词器一致——预算控制宁可多裁，不要超窗。
2. **历史压缩是规则截断，不是语义摘要**。长会话下会丢细节（ISSUE-005）。
3. **工具选择仍靠字面关键词**，对"安排…面试"这类间隔表达鲁棒性差（ISSUE-004，
   M2 阶段已由账本暴露并临时修补，根治留到 M4）。

## 6. 什么时候该推翻这个决策

出现下列任一情况时应重新评估：

- **意图识别准确率 < 90%**（M3 评测集会给出这个数）→ 换 embedding 相似度选工具
- **上下文超预算率 > 10%** 且失败用例归因到"历史被裁掉了" → 换 LLM 摘要
- 工具数量增长到 20+ → 分区比例需要重新标定，tools 分区可能要提到 30%
