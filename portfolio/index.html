01

这个项目是什么（以及不是什么）

先说清楚边界，避免误解——这本身是产品经理的基本功。

✅ 是什么

  • 一个受控 Agent 运行时：固定动作空间 + 框架层门控
  • 一套评测闭环：24 条用例 × 双裁判 × baseline 回归
  • 一个选型判断：用 Dify 做对照，说清"什么时候不该用 Dify"
  • 一份工程证据链：git 提交历史记录每一步怎么做的

❌ 不是什么

  • 不是一个 HR 系统（没有登录 / 权限 / 多租户）
  • 不接真实数据库 / 邮件服务 / 向量库（工具是 mock 实现）
  • 不是"能上线跑业务"的生产系统
诚实红线（面试必说）：这是个人项目，未上生产、无真实用户流量。文中所有通过率都是离线固定用例集的测评结果，不是上线数据。
02

为什么做这个：三个真实的痛点

Agent 不是"更聪明的聊天机器人"，它多了 Tools（改变世界）+ Controller（控制流）——这两样带来全新的风险。

① 不可控

模型可能"违规也拦不住"——发邮件、改数据这类不可逆动作，只靠提示词让模型自觉，一旦不听话就出事。

② 不可观测

出了错只能看到一段对话，定位不到"哪一步、哪个工具、入参出参"，故障无法回放。

③ 不可评测

没有固定用例集 + 冻结基线，改一行代码不知道有没有把别处改坏，更没法自证"没为了过用例而调规则"。

我的答案是：把控制权从"模型自觉"挪到"框架代码"里——门控在框架层强制、Trace 在框架层落盘、评测在框架层内置。这样"模型想违规也违规不了"这件事，是可以被评测验证的。
03

三个核心设计

每一处都有对应的验证方式——没有验证方式的约束等于没有约束。

1. 受控：动作空间固定，门控在框架层

规划器只能输出 4 种动作，任何越界的输出都被拒绝；高风险工具（发邮件 / 安排面试）在框架层被强制拦下、先出草稿，确认后才真正落地。

# harness/runner.py —— 门控不依赖模型自觉，删掉提示词也拦得住 if step.action in (ACTION_CALL_TOOL, ACTION_REQUEST_CONFIRM): spec = self.registry.get(step.tool) if spec.risk == RISK_HIGH and not self.auto_confirm: draft = self._dry_run(spec.name, step.args) # 先出草稿，零副作用 session.set_pending(spec.name, step.args) session.transition(S_AWAITING_CONFIRMATION) # 转待确认，等人 return TurnResult(status=STATUS_AWAITING_CONFIRMATION)

2. 可观测：每次运行一个 trace_id，span 树可回放

span 类型覆盖 run / plan / llm / tool_call / gate / respond，记录输入、输出、耗时、token、状态，失败能定位到具体那一步。

Trace tr-xxx （共 7 个 span） [+] run run 12.4ms [+] llm planner.decide 8.1ms 320tok [+] plan plan[0] CALL_TOOL 0.0ms [+] gate gate:schedule_interview 0.1ms ← 门控触发，可断言

3. 可评测：24 条用例 + 双裁判 + baseline 回归

四类用例各 6 条（意图与工具选择 / 条件缺口 / 门控与契约 / 内容质量），规则裁判 + LLM 裁判双轨，每条跑 3 轮测稳定性，改动后与冻结基线自动 diff。

06

Dify 对照：什么时候不该用 Dify

搭了同套 HR Agent 跑同一套评测集，结论是选型判断力，不是"Dify 不行"。

维度自研 harnessDify（对照轨）
门控性质mandatory · 代码强制advisory · 提示词建议
观测粒度durable span 树，可回放流式事件可见工具，但无 span 树 / gate / 状态机

定量 head-to-head（诚实三桶口径）

harness 主轨Dify 对照轨
重复×3×1
可比用例248（B05/B06 + D01–D06）
通过（可比内）21/24 = 87.5%7/8 = 87.5%
不可比（设计）016（工具清单 / 门控 / 状态机）
两个 87.5% 不能直接比大小。Dify 的建立在"砍掉 16 条控制面用例"之上；那 16 条恰好是 harness 100% 通过、也是其核心价值的控制面。
内容质量 Dify 5/6 vs harness 3/6，差的是所选模型 / 端点 + 提示词（Dify 用市场版 DeepSeek V4.1 Flash，harness 用官方 deepseek-chat），不是引擎能力差异。
结论一句话：Dify 是"快上线"的默认解；当出现"不可逆动作 + 必须拦得住 + 出事要能定位到那一步"时，自研受控 harness 才值回票价。
07

踩坑与调试：证明"我会定位问题"

讲"遇到什么问题、怎么定位"比讲"做了什么"更可信。

BUG-007 · 一个变量名遮蔽了内置函数

tracer.py 把参数命名为 type，遮蔽了内置 type()。只在"主逻辑先抛异常"时才二次崩溃，把 SSL EOF 的根因盖住。靠 Trace 埋点才把它从表象里挖出来。

BUG-008 · 外部调用没有重试

DeepSeek 一次瞬断 SSL EOF 就让整轮评测判死。补了 3 次指数退避 + 抖动重试，只对 429/5xx/网络错误重试。修后 87 次调用 0 异常。

BUG-004/005 · 关键词的两面

字面匹配既会漏选（"安排明天下午面试"命中不了）也会误选（"候选人"误导进查简历）。改成强弱信号加权打分 + 全局阈值，并用独立探针自证没过拟合。

Dify 联调三连坑

Cloudflare 按 UA 封机器人（403/1010）；Agent 应用只支持 streaming（blocking 被 400 拒）；自定义工具只收 OpenAPI，不能直接贴 mock 代码。
