PRD · HRAgent Harness

一个可观测、可评测的受控 Agent 运行时

项目 内容
项目代号 HRAH（HRAgent Harness）
一句话定位 一个自己写的 Agent 运行时 + 一套给它打分的评测体系，用 HR 招聘场景验证
文档版本 v0.1（草稿）
状态 开发中 · M4 工具选择策略已重构并通过回归；接 DeepSeek 真模型待 API Key
日期 2026-10-05
性质声明 个人独立项目，非公司产品，未上生产，无真实企业用户与流量

0. 文档说明

0.1 这份 PRD 定义什么

本 PRD 定义 HRAH 是什么、为谁做、解决什么问题、包含哪些能力、怎么算做对了。

它不是一份"HR 系统"的 PRD。HR 招聘（JD 生成、简历筛选、面试安排、邮件通知）在本项目中是验证场景，不是产品本体。产品本体是让这些任务能被稳定、可控、可追溯地完成的运行时，以及证明它确实做到位的评测体系。

0.2 为什么这样定位

企业里落地 AI Agent 时，真正的难点从来不是"接一个大模型"，而是四件没人愿意做的事：

难点 具体表现
不可控 模型想调什么工具就调什么，动作空间没有边界
不可观测 结果错了，说不清是哪一步错的，只能重跑一遍碰运气
不可评测 "感觉还行"就算验收，改一版 prompt 不知道是变好还是变坏
上下文失控 聊几轮就爆 token，或者关键信息被历史挤掉了

本项目的目标就是把这四件事做成显式设计，并在一个真实场景里跑出可验证的数据。

0.3 参考与致谢

本项目为个人独立设计与实现。设计思路参考了：

  • 一门 AI 产品落地课程提供的 HR Agent 案例材料（产品文档与参考实现），用于理解业务场景与评测框架的组织方式
  • Dify 等开源/商用编排平台的公开设计
  • 社区关于 Agent 评测、上下文工程的公开实践

本项目的代码、评测集、架构决策均为独立编写，未复制课程提供的源码。 课程参考实现在本项目中仅作为对照基线存在（见第 10 节）。

1. 产品概述

1.1 一句话说清

HRAH 是一个让 AI Agent 干活"有边界、看得见、测得准"的运行时：用户（HR）用一句话下达任务，系统在固定的动作空间内决定该调什么工具、缺什么信息就追问、涉及高风险动作先停下等人确认，并且每一次决策都留下可回放的 Trace；配套一套评测体系，用固定用例集反复跑，量化它到底靠不靠谱。

1.2 解决什么问题

# 问题 现状做法 HRAH 的做法
P1 Agent 动作无边界 提示词里写一句"你可以用这些工具"，靠模型自觉 工具注册表 + 固定动作空间，注册表外的调用一律拒绝
P2 出错定位不了 只看最终输出，中间过程黑盒 结构化 Trace：意图 → 规划 → 每次工具调用 → 门控 → 响应，全链路可回放
P3 改一版不知道好坏 人工抽几条试试 固定用例集 + 规则/LLM 双裁判 + 多次重复运行 + baseline 回归
P4 上下文失控 历史全量塞进去，爆了就截断 显式 token 预算分配 + 分层裁剪与摘要策略
P5 多轮任务没有状态 每轮当成新对话，流程接不起来 显式会话状态机，状态驱动行为
P6 高风险动作没人管 直接执行，错了不可逆 风险分级 + 人工确认门控，门控 100% 触发

1.3 产品价值（对三类对象）

对象 价值
HR 使用者 一句话下达招聘任务，缺信息系统会追问，发邮件/安排面试一定会先问过人
开发者（我自己） 得到一个能讲清每一个设计取舍的 Agent 运行时，而不是一个调不通的黑盒
评审/面试官 能看到完整的设计文档、可运行代码、真实评测数据与失败归因，而非一段描述

1.4 成功标准（本项目自设目标，非行业标准）

维度 目标
功能 4 个 HR 任务端到端跑通，引擎与场景解耦
可控性 工具调用 100% 落在注册表内；高风险动作门控触发率 100%
可观测 每次运行产出完整 Trace，Trace 完整率 100%，可单条回放
可评测 24 条用例 × 3 轮，输出通过率、稳定性、失败模式分布
可复现 换一台机器、换一个模型，同一套命令能跑出同样的报告

2. 产品边界

2.1 范围内

层级 模块
场景层 JD 生成、简历筛选、面试安排、邮件通知（4 个任务）
引擎层 工具注册表、受控规划器、上下文管理器、会话状态机、Trace、人工门控
评测层 用例集、裁判（规则 + LLM）、多次重复运行、baseline 回归、报告生成
对照层 Dify 工作流实现同一批任务，作为基线对照
呈现 一个轻量看板（评测报告 + Trace 回放），不追求视觉

2.2 明确不做（P0 声明，避免范围膨胀）

  • ❌ 不做完整 HR SaaS：没有登录鉴权、没有多租户、没有角色权限体系、没有组织架构
  • ❌ 不做真实邮件发送：邮件工具为 mock，落草稿文件即可，不接真实 SMTP
  • ❌ 不做 RAG 深度优化：知识检索用最简实现（本地向量库或关键词），重点不在检索算法
  • ❌ 不做前端工程：一个轻量看板足够，不写 Vue/React 全家桶
  • ❌ 不做模型训练/微调：只用现成 LLM API
  • ❌ 不做线上部署与真实用户试用：本地可运行即为完成标准

说明：这些"不做"是主动的范围裁剪，不是能力缺失。裁剪原则是——凡是不能证明"Agent 运行时能力"的工作，一律砍掉。

2.3 三条设计底线

  1. AI 不替人做最终决定：高风险动作必须经人工确认，确认前只出草稿。
  2. 一切行为可追溯：任何一次运行都能还原完整决策链路。
  3. 一切结论有数据：不出现"效果不错"这类无法验证的表述，所有结论来自评测报告。

4.2 引擎层模块清单

模块 职责 关键设计
tool_registry.py 声明可用工具，定义参数契约与风险等级 注册表外调用一律拒绝；按意图只注入相关工具定义
planner.py 决定下一步动作（调工具 / 追问 / 请求确认 / 结束） 受控 ReAct：动作空间固定为 4 种，不允许自由发挥
context_manager.py 组装每次请求的上下文，控制 token 预算 分区预算 + 分层裁剪 + 早期历史摘要
session_state.py 维护会话状态与槽位（已收集的信息） 显式状态机，状态驱动行为
tracer.py 记录每次运行的完整链路 trace_id + span 树，含输入/输出/耗时/token/状态
gate.py 高风险动作的人工确认门控 风险分级，高风险必拦

4.3 双轨设计（自研 harness vs Dify）

同一批 HR 任务有两条实现路径，跑同一套评测集：

自研 harness Dify 工作流（云端版）
定位 主轨道，展示引擎能力 对照组，现成编排平台基线
实现 Python，约 20 文件 云端可视化编排 + API 调用
评测 同一套 24 条用例、同一套裁判 同左

对照结论将沉淀为一篇 ADR：《什么情况下必须自研 harness，什么情况下用 Dify 就够了》。

5. 功能需求

5.1 工具注册表（FR-001 组）

工具是 Agent 唯一被允许执行的动作来源。

工具名 说明 风险等级 需人工确认
generate_jd 生成岗位 JD 初稿 低 否
generate_rubric 生成简历评分标准 低 否
screen_resume 结合 JD 与评分标准给简历打分 低 否
generate_interview_plan 生成结构化面试方案 低 否
search_knowledge 检索制度/知识库 低 否
get_candidate 查询候选人信息 低 否
draft_email 生成邮件草稿（不发送） 中 否
schedule_interview 安排面试 高 是
send_email 发送邮件 高 是

每个工具声明包含：名称、描述、参数 JSON Schema、风险等级、返回结构、失败语义。

5.2 受控规划器（FR-002 组）

规划器的动作空间固定为 4 种，不允许其他输出：

动作 含义
CALL_TOOL 调用注册表中的某个工具
ASK_USER 向用户追问缺失信息
REQUEST_CONFIRM 请求人工确认高风险动作
FINISH 结束并给出最终回应

5.3 条件缺口三分类（FR-003 组）

当任务无法直接执行时，判断缺口类型并采取不同策略：

类型 判断依据 系统行为
MISSING_INFO 缺用户输入（如没说岗位、没说候选人） 追问，一次只问最关键的 1~2 项
MISSING_PREREQUISITE 缺前置产物（如没 JD 就要筛简历） 说明缺什么，引导先完成前置
MISSING_CONFIRMATION 信息齐全但动作高风险 出草稿 + 请求确认

5.4 上下文管理（FR-004 组）

Token 预算分配（占模型窗口比例）

分区 预算 裁剪策略
系统提示 15% 固定，不裁剪
工具定义 20% 只注入与当前意图相关的 top-k 工具
检索片段 25% 按相关度截断，标注来源
对话历史 30% 近 3 轮保留原文，更早部分压缩为摘要
生成预留 10% 不可占用

超出预算时必须记录一次 context_truncated 事件到 Trace。

5.5 会话状态机（FR-005 组）

IDLE ──> INTENT_RESOLVED ──> PLANNING ──> EXECUTING ──> DONE
              │                  │             │
              │                  ↓             ├──> FAILED
              │          AWAITING_INPUT        │
              │          AWAITING_CONFIRM      └──> ESCALATED
              └──> CLARIFYING

5.6 Trace（FR-006 组）

  • 每次运行生成唯一 trace_id
  • Span 类型：intent / plan / tool_call / gate / respond
  • 每个 span 记录：父 span、类型、输入摘要、输出摘要、耗时、token 数、状态
  • 支持按 trace_id 单条回放，输出人类可读的时间线

5.7 评测体系（FR-007 组）

用例集（24 条，分 4 类）

类别 条数 考察点
A · 意图识别 6 能不能听懂要办什么事
B · 缺口处理 6 缺信息/缺前置/缺确认的分类是否正确
C · 工具调用与门控 6 参数是否合法、高风险是否拦住
D · 内容质量 6 产出内容是否可用

双裁判

裁判 适用 特点
规则裁判 A/B/C 类 确定性判定，可复现
LLM 裁判 D 类 评分 + 理由，重复 3 次取多数

运行方式：每条用例重复 3 轮，计算一致率（稳定性）；支持 --baseline 与历史版本对比。

6. 核心流程

6.1 Agent 执行主链路

1. 用户输入
2. 意图识别 ──────────> 不确定则进入 CLARIFYING
3. 收集槽位信息
4. 缺口判断 ── 缺信息 ──> ASK_USER，回到 1
              └─ 缺前置 ──> 提示前置，结束本轮
5. 规划：选工具（仅注册表内）
6. 风险判定 ── 高风险 ──> REQUEST_CONFIRM（出草稿）
                          └─ 用户拒绝 ──> 取消
                          └─ 用户同意 ──> 继续
7. 执行工具，结果写入 Trace
8. 结果整合，回到 4 直到无缺口
9. FINISH，给出最终回应

6.2 需要覆盖的异常场景

场景 期望行为
用户要求调用注册表外的能力 明确说明不支持，不臆造工具
工具执行失败 记录失败 span，重试一次，仍失败则上报原因
用户拒绝高风险确认 取消动作，保留草稿，不残留副作用
上下文超预算 触发裁剪并记录事件，不静默丢信息
模型输出非法动作 拒绝执行，记为规划失败并重试一次

7. 需求描述（EARS 格式）

通用约束（Ubiquitous）

  • FR-001：系统应当只允许调用工具注册表中声明的工具。
  • FR-002：系统应当为每次运行生成唯一 trace_id，并保证链路完整。
  • FR-003：系统应当保证高风险动作在执行前必须经过人工确认。

事件驱动（Event-driven）

  • FR-004：当用户提交一条新指令时，系统应当先进行意图识别，并在置信度不足时进入澄清状态。
  • FR-005：当识别出任务缺少必要输入时，系统应当以 MISSING_INFO 处理，并一次只追问最关键的 1~2 项。
  • FR-006：当识别出任务缺少前置产物时，系统应当以 MISSING_PREREQUISITE 处理，并说明需要先完成什么。
  • FR-007：当规划结果为高风险工具调用时，系统应当生成草稿并请求人工确认。
  • FR-008：当用户拒绝确认时，系统应当取消该动作且不产生任何副作用。
  • FR-009：当工具调用失败时，系统应当记录失败 span，重试一次，仍失败则向用户说明原因。
  • FR-010：当模型输出不在允许动作空间内时，系统应当拒绝执行并记为规划失败。

状态驱动（State-driven）

  • FR-011：当会话处于 AWAITING_CONFIRMATION 状态时，系统应当暂停执行，仅等待确认或取消。
  • FR-012：当会话处于 AWAITING_INPUT 状态时，系统应当保存已收集的槽位信息，不被新输入清空。

异常（Unwanted）

  • FR-013：如果上下文组装超出 token 预算，则系统应当按分区策略裁剪，并在 Trace 中记录 context_truncated 事件。
  • FR-014：如果用户请求的能力不在注册表中，则系统应当明确告知不支持，不得臆造工具或编造结果。
  • FR-015：如果评测运行中出现裁判不可用，则系统应当标记该条用例为"未判定"，不得计入通过率。

可选（Optional）

  • FR-016：在配置开启 Dify 对照模式时，系统应当用同一套用例集调用 Dify 工作流并输出对照报告。

8. 数据指标与成功度量

8.1 北极星指标

可控完成率 = 在固定用例集上，「任务完成 且 全程动作合规」的比例。

选它的理由：单纯的任务完成率会掩盖"蒙对了但过程违规"，而 Agent 落地的风险恰恰来自过程不可控。

8.2 指标表

指标 定义 目标值 备注
意图识别准确率 A 类用例意图判定正确比例 ≥ 90% 24 条固定用例集
契约通过率 工具调用参数合法、且在注册表内 100% 硬指标，不允许例外
门控触发率 高风险动作触发确认的比例 100% 硬指标
门控误伤率 低风险动作被误拦的比例 ≤ 10% 避免过度打扰
稳定性 同一用例 3 轮结果一致率 ≥ 90%
Trace 完整率 能完整回放的运行占比 100% 硬指标
可控完成率 完成且全程合规 ≥ 80% 北极星
上下文超预算率 触发裁剪的运行占比 ≤ 10%
失败可定位率 失败用例能归因到具体模式的比例 ≥ 90% 对照 Dify 的关键差异项

⚠️ 以上目标值为本项目自设目标，用于驱动迭代，不是行业验收标准，也不代表线上表现。

9. 验收标准

9.1 功能验收

# 验收项
1 4 个 HR 任务端到端可执行，输出可人工判读
2 9 个工具全部在注册表中声明，注册表外调用被拒绝
3 三类缺口（信息/前置/确认）各有至少 2 条用例被正确处理
4 每次运行可导出一条完整 Trace 并回放
5 上下文超预算时能观察到裁剪事件

9.2 评测验收

# 验收项
6 24 条用例全部可执行，无"未判定"残留
7 3 轮重复运行可完成，输出稳定性数据
8 存在一次真实的"优化 → 回归"记录（改前后指标对比）

ADR-001 · 上下文按分区预算管理，预算不足时按固定顺序裁剪

  • 日期：2026-10-05
  • 状态：已接受（M2 已实现）
  • 关联：PRD 5.4 / FR-004 / FR-005 / FR-006 / FR-013

1. 背景与问题

M1 的做法是"固定注入 top_k=5 个工具 + 历史对话全量拼接"。跑起来之后暴露两个问题：

  1. 无关工具白吃 token：写 JD 时把 draft_email、generate_rubric 也塞进去了 （因为它们得分是 0，但 top_k 要求凑满 5 个）。实测每次注入 5~7 个工具， 其中大多数与当前意图无关。
  2. 历史无上限增长：多轮对话后历史会无节制地把预算吃光， 要么撑爆窗口，要么把工具定义挤掉——而工具定义被挤掉会导致模型臆造工具。

根因是：上下文从未被当作一项有额度的资源来管理，各段内容的增长互不相让。

2. 决策

2.1 分区预算

把一次规划调用的窗口切成 5 个区，每区独立额度：

分区 比例 裁剪策略
system 15% 固定成本，不裁剪（超了只记备注）
tools 20% 只注入相关性得分 > 0 的工具；超预算按相关性从低到高裁剪
retrieval 25% 按相关度顺序截断尾部片段
history 30% 与"本轮执行结果"共享；先压缩早期轮次，仍超则丢弃最旧
reserve 10% 不可占用

2.2 三条裁剪优先级（这条是本 ADR 的核心）

  1. 执行结果优先于历史对话 —— 本轮已经调了什么工具、返回了什么， 是当前决策的直接依据；早期客套话不是。
  2. 高风险工具永不裁剪 —— schedule_interview / send_email 即使撑爆工具分区 也必须注入。理由见第 3 节。
  3. 宁可压缩，不要静默丢弃 —— 压缩会留下"这里曾有 N 条消息"的痕迹， 静默丢弃不会。任何一次裁剪都必须写进账本与 Trace。

2.3 每次运行产出账本

ContextPackage 记录：各分区用量/上限、注入了哪些工具、裁掉了哪些、 历史压缩与丢弃条数、备注。账本进 Trace 的 context.build span， 也能在终端用 python demo.py --context 直接打印。

3. 关键取舍：为什么高风险工具不受预算约束

这是安全优先于成本的取舍。

工具定义被裁剪的直接后果不是"少一个功能"，而是模型不知道这个能力存在， 于是自己编一个。在 HR 场景里，一个被臆造出来的"发邮件"比多花 300 个 token 危险得多——前者可能产生真实的对外副作用。

代价：工具分区的实际占用可能超过 20%。这个代价被显式接受， 并在账本里以备注形式暴露，而不是悄悄吞掉。

4. 被否决的备选方案

方案 否决理由
全量注入 9 个工具，不筛选 工具定义随工具数线性膨胀；9 个还好，50 个就不可行。且无关工具会干扰模型选择
固定 top_k（M1 现状） top_k 是个拍脑袋的数：凑不满时会硬填无关工具，正好时能用的也可能被切掉
超预算时直接截断整个历史 静默丢信息，出问题无法归因。违反 PRD 三条设计底线里的"一切行为可追溯"
每轮都用 LLM 做历史摘要 多一次模型调用 = 多一份延迟与成本，且摘要本身可能丢关键信息。当前规模下不划算；留到 M4 用数据决定
embedding 相似度选工具 效果更好，但要引入向量依赖与额外调用，破坏"零依赖可跑"的约束。留到 M4 接真模型时一并评估

5. 代价与已知局限

  1. token 估算是粗估（CJK 按 1 字 ≈ 1 token，其余 4 字符 ≈ 1 token，刻意高估）。 不追求与真实分词器一致——预算控制宁可多裁，不要超窗。
  2. 历史压缩是规则截断，不是语义摘要。长会话下会丢细节（ISSUE-005）。
  3. 工具选择仍靠字面关键词，对"安排…面试"这类间隔表达鲁棒性差（ISSUE-004， M2 阶段已由账本暴露并临时修补，根治留到 M4）。

6. 什么时候该推翻这个决策

出现下列任一情况时应重新评估：

  • 意图识别准确率 < 90%（M3 评测集会给出这个数）→ 换 embedding 相似度选工具
  • 上下文超预算率 > 10% 且失败用例归因到"历史被裁掉了" → 换 LLM 摘要
  • 工具数量增长到 20+ → 分区比例需要重新标定，tools 分区可能要提到 30%

7. 实测结果

python scripts/context_benchmark.py（5 个场景 × 4 档历史长度）：

指标 结果
上下文 token 平均降幅 36.0%
工具注入数量（历史 0 条） M1 5~7 个 → M2 2~3 个
历史 24 条时 压缩 20 条，历史 token 766 → 629

详见 reports/context_benchmark.md。

说明：用例与对话历史均由本项目自造，用于验证机制是否生效，不代表真实线上分布。

ADR-002 · 工具选择策略：为什么放弃「高风险工具强制注入」

  • 状态：已采纳（M4 实现并有评测数据支撑）
  • 日期：2026-10-05
  • 相关：ADR-001 上下文预算与裁剪策略、BUG-004 / BUG-005 / ISSUE-006、评测用例 A04 / A05 / A06
  • 影响范围：harness/tool_registry.py、harness/context.py、tools/hr_tools.py

1. 背景

ContextManager 需要在每一轮决定「把哪些工具的定义摆到模型面前」。 这个决定同时牵动三件事：token 成本、正确性、安全性。

M3 的评测集把它变成了可度量的东西，于是立刻暴露出两个方向相反的问题：

用例 现象 对应缺陷
A04「给张三安排明天下午面试」 该选的没选上，靠兜底逻辑蒙混过关 BUG-004 漏选
A05「发邮件通知候选人面试时间」 不该选的被塞进来（get_candidate） BUG-005 误选
A06「帮我准备 Java 岗的面试问题」 不该选的被塞进来（schedule_interview） ISSUE-006 过度兜底

漏选和误选是同一根因的两面：字面匹配没有语义。 只看「有没有匹配上」，等于把问题从一头推到另一头还自我感觉良好。

2. 三级演进

阶段 做法 结果
M1 固定注入 top_k=5 个工具，得分 0 也塞进来 + 高风险工具无条件追加 写 JD 时把 draft_email 也摆上桌，白占 token
M2 相关性阈值 + 分区预算裁剪 + 历史压缩 token 降下来，但两个相邻 bug 被账本逼出来
M4 强弱信号加权打分 + 全局阈值 + 取消强制注入 A05/A06 转绿，同一批准则下 tools token 再降一档

3. 决策一：强弱信号加权打分 + 全局阈值

规则

strong（+3）  「动作 + 对象」的短语，用正则表达、允许中间插入修饰语
weak  （+1）  单个泛词，区分度低
门槛  （ 3）  至少命中一个强信号才入选

为什么是这样

中文的「动词 + 宾语」天然不连续。 这是所有难度来源：

r"安排.{0,10}?面试"          # 吃下「安排明天下午面试」
r"候选人.{0,6}?(状态|进展|…)"  # 吃下「候选人王五现在进展到哪一步了」
r"简历.{0,8}?(…|打.{0,2}?分)"  # 吃下「这份简历请打个分」

泛词必须降权，不能和短语同权。 「候选人」三个字出现在句子里，可能是查询意图，也可能只是宾语。 把它和「候选人状态」放在同一权重里（M1~M3 就是这样），本质上是在说 「出现即相关」——这是 BUG-005 的根因。

配套：命中说明写进账本

每次选择都会记录「命中了哪个信号、得了几分」，例如：

工具命中: send_email=6 分，schedule_interview=4 分

理由：事后解释不清的选择，等于给调试留了个黑洞。 BUG-004 就是靠账本的一条备注才被发现的。

4. 决策二：取消「高风险工具强制注入」

这是本 ADR 的重点。

原来的做法与理由

# M1~M3 的代码
for spec in self._tools.values():
    if spec.risk == RISK_HIGH and spec.name not in picked:
        picked.append(spec)

当初的理由是：模型必须知道这些能力存在，否则会臆造工具（自己编一个不存在的能力去满足用户）。

为什么不成立

防臆造这件事，在 system prompt 里已经做了：

需要调用清单以外的能力时，直接 FINISH 并说明不支持。

一句话就能覆盖的行为，不需要牺牲上下文预算去买。而强制注入的代价是三项：

  1. 白占 token：5 个典型场景里 4 个是多余的，每个约 100 token。
  2. 诱导误触高风险动作（这条比省 token 重要得多）： 把「发邮件」摆在模型面前，用户问的是「帮我准备面试问题」， 模型也可能顺手去发——每误触一次就弹一次人工确认，等于打断用户。
  3. 污染评测信号：工具列表里永远有高风险工具，让「是否误选」这类断言很难测准。

失败方向的取舍

取消之后，万一某句话确实需要高风险工具但没匹配上（比如用户说「就这么定了」）， 模型会 FINISH 说明不支持。

这是可以接受的失败方向：宁可少做一步让人补一句，不可自作主张发一封收不回的邮件。 这条性质和 FR-007（高风险动作先出草稿）是一致的。

保留的部分

被选中（确实相关）的高风险工具，在工具分区预算不足时仍然不被裁剪—— 安全优先于预算这条没有变。变的只是「无条件入场券」。

5. 被否决的方案

否决：embedding / 向量相似度

理由 说明
成本 引入新的 Key、依赖、延迟，而这一步非常轻，不值当
指标体系 更关键的一点：一旦用模型做工具选择，A 类指标就不再是「与模型无关的引擎指标」。评测从"测引擎"变成"测模型"，整个 A/B/C/D 分层的定义就散了
可解释性 向量相似度给不出「为什么选了它」，出问题时只能盲猜

否决：LLM 路由器（用模型选工具）

同上，外加多一次 LLM 调用（成本与延迟翻倍）。

但这两条不是永久否决。 见第 7 节的推翻条件。

6. 验证

6.1 评测集回归

通过率 85% → 100%
新增失败：无
新修好  ：A05、A06

其中关键的负向验证：C 类 6 条全绿。 说明取消强制注入之后，该拦的照样拦——安全性没有被削弱，减少的只是跟着准入的那部分冗余。

6.2 独立探针（自证不是过拟合）

改完策略让两条红用例变绿，本身不能证明修好了根因—— 把规则调得刚好能过已知用例，同样能变绿。

所以 scripts/tool_select_probe.py 用了一批措辞与 evals/cases.py 完全不同的句子重测：

通过 18/18，准确率 100%

探针里刻意包含了两类句子：

  • 修复点的 positives：发 email 通知候选人下周来面试 → 不得注入 get_candidate
  • 防止矫枉过正的 inverse：候选人王五现在进展到哪一步了 → 必须仍注入 get_candidate

第二类尤其重要：修误注入最容易犯的错，就是把正例也一起打死。

6.3 上下文收益（忠实基线复算）

平均降幅 52.8%，注入工具数 6.4 → 1.2 个

基线是在 benchmark 脚本里独立冻结复算的，不调用当前实现。 这件事本身踩过一个坑，见调试日志 BUG-006。

7. 已知边界与推翻条件

这套方案做不到的事

  • 否定句：「先别发邮件，我一会自己通知」→ 发…邮件 命中，会被误判为肯定意图。 字面匹配的固有缺陷，不是实现 bug。
  • 省略主语的承接：「就这么定了」→ 无强信号 → FINISH。属于上文依赖，需要会话状态参与判断。
  • 同义改写：「招募启事」≠「招聘启事」。可以靠持续扩充 strong 缓解，但不能根治。

什么情况下应该推翻本 ADR

出现下列任一情况时，应改用 embedding 或 LLM 路由：

  1. 工具数量增长到 30 个以上（手写规则维护不动了）
  2. 真实语料下工具选择的漏选率 > 5%
  3. 出现多轮依赖的工具选择需求（需要跨轮意图）

届时正确做法是：把新方案做成可选开关，用同一套评测集 + 探针集跑对比， 用 A 类指标决定胜负——而不是拍脑袋换。

8. 一句话总结

工具选择这件事上，「存在感」不需要靠无条件的入场券来保证， 而应该由信号强度决定。省下来的 token 是顺带的收益， 真正的收益是不再诱导模型去碰它本不该碰的高风险动作。

ADR-003：什么时候不该用 Dify（以及什么时候该用）

项 内容
状态 已接受（Accepted）——定性结论已基于代码级对比 + Dify 云端实测成立；定量 head-to-head 已跑通（可比维度 B 2/2 + D 5/6；A/C 共 16 条设计不可比不计入通过率）
决策人 程枢（本项目引擎作者）
时间 2026-10-05
关联 docs/00-PRD-受控Agent运行时.md（FR-003/FR-007 高风险门控、FR-002 Trace）、docs/04-Dify对照工作流搭建说明.md、evals/dify_adapter.py

1. 背景（为什么要有这篇 ADR）

M5 设立一条对照轨：在 Dify 云端版（dify.ai）照着自研 harness 的 9 个工具、同一套提示词，搭一个等价的 HR 招聘 Agent，跑同一套 24 条评测集，看两条轨道差异在哪。

设立对照轨的目的不是"证明 Dify 不行"——Dify 是成熟的编排平台，能极大缩短从 0 到 1 的时间。目的是证明选型判断力：在什么约束下自研 harness 是更对的那个选择，在什么约束下根本不该自己造轮子。

本 ADR 是 M5 的落点文档。结论分两层：什么时候不该用 Dify（用自研） 和 什么时候该用 Dify（别自己造）。

2. 决策（一句话）

当需求存在高风险动作需要代码级强制拦截、需要 span 级可回放定位故障、或工具是自研代码而非现成 HTTP 服务这三类约束中的任意一种时，Dify 的"软管控 + 会话级观测"模型会暴露短板，应来自研受控 harness；否则用 Dify 更快、更稳、更省。

3. 论据与证据

论据一：控制强度 —— mandatory（代码强制）vs advisory（提示词建议）

自研 harness（mandatory）

门控写在 harness/runner.py 的框架主循环里，不依赖模型自觉：

# harness/runner.py L186-202
if step.action in (ACTION_CALL_TOOL, ACTION_REQUEST_CONFIRM):
    spec = self.registry.get(step.tool)
    # 门控：高风险一律拦下（FR-003）
    if spec.risk == RISK_HIGH and not self.auto_confirm:
        draft = self._dry_run(spec.name, step.args, tracer, root.span_id)  # 先出草稿，零副作用
        session.set_pending(spec.name, step.args)
        session.transition(S_AWAITING_CONFIRMATION, reason="高风险动作待人工确认")
        return TurnResult(status=STATUS_AWAITING_CONFIRMATION, ...)

关键性质：

  • 拦截发生在框架层，不是提示词层。即使模型直接输出 CALL_TOOL send_email，runner 也因 risk == RISK_HIGH 拦下转待确认，并先调 _dry_run(confirmed=False) 出草稿，确认前零副作用（评测侧断言 no_side_effect=True）。
  • 删掉提示词也拦得住。这是"受控"二字的落点，可用评测验证"模型想违规也违规不了"。

Dify（advisory，实测）

M5 在 dify.ai 搭 HRAH-Dify-Control 时的两次实测：

  • 踩坑3（已确认）：翻遍 Agent 配置（工具菜单、悬停、高级设置），没有"人工确认 / 工具调用前确认"开关。该版 Dify Agent 无原生"工具调用前代码级拦截"。
  • 踩坑4（已确认）：输入"发邮件通知候选人面试时间"，Dify Agent 确实暂停并逐项追问收件人/岗位/时间/形式，并声明"发送邮件属高风险，未经确认不发出"——但这个"安全"完全由提示词让模型自觉驱动。把提示词删了、或换一个没那么听话的模型，Dify 会直接把邮件发出去。
  • 补充发现（shell_run，实测）：用 scripts/_dify_probe.py 发同一条 query 时，Dify Agent 除了我们显式添加的 send_email，还自行调用了内置工具 shell_run（在 Dify 沙箱里执行了一段探查脚本，observation 回的是沙箱元数据）。说明 Dify Agent 的可调工具面不完全由用户显式注册控制——平台内置工具也在其可调范围内。这进一步坐实"控制面在 Dify 手里（advisory）"而非"在我代码里（mandatory）"。

结论（精确表述，不夸大）：不是"Dify 没安全"，而是 Dify 在这条轨道上提供的是 advisory（建议性）控制——安全靠提示词 + 模型自觉，且可调工具面含平台内置项；harness 提供的是 mandatory（强制性）控制——安全靠代码，删提示词也生效，且工具面完全由 ToolRegistry 显式注册。对发邮件 / 改生产数据 / 转账这类不可逆高风险动作，mandatory 是更稳的选择。

论据二：可观测性 —— span 级（可回放）vs 会话级（仅摘要）

自研 harness（span 级）

harness/tracer.py 每次运行一个 trace_id，span 类型覆盖 run / plan / llm / tool_call / gate / respond，每个 span 记输入、输出、耗时、token、状态。summary() 直接给可度量信号：

# harness/tracer.py L155-168
"span_count": len(self.spans),
"tool_calls": sum(1 for s in self.spans if s.type == SPAN_TOOL),
"gate_count": sum(1 for s in self.spans if s.type == SPAN_GATE),
"failed_spans": sum(1 for s in self.spans if s.status == "failed"),
"repaired_spans": sum(1 for s in self.spans if s.status == "repaired"),

失败能定位到"哪一步、哪个工具、入参出参是什么"。这正是 PRD 北极星指标失败可定位率的来源，也是 M4 能靠 Trace 把 BUG-007（tracer 遮蔽内置 type）从 SSL EOF 的表象里挖出来的原因。

Dify（流式事件，实测校正）

  • 踩坑5（实测）：打开 Dify 的「日志 / 监控」页面，用户报告"日志显示暂无日志"；即便有数据，日志表头列是会话级字段：标题 / 来源 / 终端用户 / 消息数 / 用户评分 / 操作率 / 更新时间 / 创建时间——没有工具调用明细列、没有 token 列、没有 span 树列、没有门控次数列。
  • 校正（2026-10-05 实测，重要）：此前版本以为 Dify "完全看不到工具调用"。实测用 scripts/_dify_probe.py 跑 streaming 后发现：Dify Agent 的 streaming 响应会在 agent_thought 事件里带 tool / tool_input / observation——也就是说"调了哪个工具、观察结果是什么"在流式传输时是可见的。这一点比最初设想好，适配器已据此从 agent_thought 抽取 tools_called（见 evals/dify_adapter.py 的 _read_stream / _normalize）。
  • 但 Dify 暴露的工具调用是一次性流式事件，不是持久化、可查询、带类型的 span 树： 1. 没有 gate_count 概念——"门控有没有触发"无从断言； 2. 没有 span 类型（run/plan/llm/tool/gate…）——失败只能看整段对话，定位不到"哪一步、哪个工具、入参出参"； 3. 不建模 awaiting_confirmation / awaiting_input / 副作用（scheduled/sent）——控制流信号缺失； 4. 日志页只落会话级摘要（踩坑5），流式事件不进可回放日志。
  • 适配器侧印证：_normalize() 现在会从 agent_thought 抽 tools_called，但 gate_count=0 / span_count=1 / scheduled=[] / sent=[] 仍无法从 Dify 取得——这正是 C 类在 Dify 侧标记「不可比（设计）」、不计入通过率的根因（evals/dify_adapter.py 的 _dify_incomparable）。

结论（精确表述，不夸大）：不是"Dify 看不到工具调用"，而是 Dify 给的是传输时的流式事件（工具可见、但无类型、无门控、无状态机、不可回放）；harness 给的是持久化、带类型、可回放的 span 树（含 gate_count / failed / repaired）。当故障需要"定位到具体一次工具调用为什么会失败"时，流式事件不够用——尤其 gate_count 这类控制流断言完全无法从 Dify 取得。

论据三：工具接入模型 —— 自研代码 vs 必须包装成真实 HTTP API

踩坑2（已确认）：Dify 点工具面板右上「+」进「创建自定义工具」，该框只接受 OpenAPI / Swagger schema，面向"调真实 HTTP API"。不能直接粘贴一段 mock / 自研代码。

对策（已跑通）：把 servers.url 指向公共回显 https://httpbin.org，path /anything/send_email，无需自建服务器即把工具接进 Dify。

对比 harness：harness/tool_registry.py 的 ToolRegistry 接收任意 Python 可调用对象（spec.call(**args)），9 个 HR 工具全是本地 mock，hr_tools.py 一行 build_registry() 即注册，零部署。

结论：Dify 接现成 HTTP 服务极顺；接自研逻辑 / mock / 还没暴露成服务的内部能力要先补一层 API 包装。harness 在这类"工具还在我代码里"的场景下零摩擦。

论据四（次要）：可回归性 —— 自带评测闭环

harness 每层改动都能用 scripts/run_evals.py（24 条 × 3 轮 + baseline 回归）量化回归，M3→M4 就是靠它从 85% 拉到 100% 并自证没过拟合（探针 18/18）。Dify 工作流的"改完还安全吗"只能靠人工回归或另搭评测，没有内建的、可冻结基线的评测闭环。

5. 后果（选错会失去 / 付出什么）

选 harness（自研）会付出的代价

  • 要自己写引擎、状态机、Trace、门控——工作量远大于在 Dify 拖节点。
  • 要自己维护工具注册、上下文裁剪、评测闭环。
  • 非高风险、工具都是现成 HTTP 服务、对观测粒度要求不高的场景，自研是过度工程。

选 Dify 会失去的（即 harness 的卖点）

  • 高风险动作失去代码级强制拦截（只剩提示词建议）。
  • 故障失去 span 级回放，只能看会话摘要。
  • 自研逻辑要先包成 HTTP API 才能接进来。
  • 改动失去内建可冻结基线的回归评测。

6. 被否决的方案

  • 方案 A：用 Dify 替代 harness 做主轨。否决理由：主轨要展示的是"引擎可控性"，而 Dify 的管控是 advisory，无法用评测证明"模型想违规也违规不了"，与项目北极星（可控完成率 / 失败可定位率）冲突。
  • 方案 B：两条轨道都不要，纯用 Dify。否决理由：失去 M5 要证明的"选型判断力"证据，也失去 span 级观测这个面试可讲的设计落点。
  • 方案 C：在 Dify 里手写代码节点做门控。云端版 Agent 模式不支持直接贴代码（踩坑2），需自建 API 服务，成本接近自研且更绕。

7. 决策规则（给面试官的"选型检查表"）

条件 选 Dify 选自研 harness
高风险动作需代码级强制拦截 ✅
需要 span 级故障回放 ✅
工具是自研代码 / mock / 未暴露成服务 ✅
要内建可冻结基线的回归评测 ✅（已建）
从 0 到 1 要快、工具都是现成 HTTP 服务 ✅
对观测粒度要求不高、团队不会 Python 引擎 ✅
要借平台生态（知识库 / 多模型 / 发布渠道） ✅

一句话：Dify 是"快上线"的默认解；当出现"不可逆动作 + 必须拦得住 + 出事要能定位到那一步"时，自研受控 harness 才值回票价。

8. 推翻条件（什么情况下本 ADR 要重议）

  1. Dify 后续版本在 Agent 模式加了原生工具调用前确认 / 代码级门控（API 可断言），则论据一弱化，需重测。
  2. Dify 开放工具调用 / token / span 级日志 API（非仅会话级），则论据二弱化。
  3. 本项目需求从"招聘高风险动作"转向"低风险问答机器人"，mandatory 控制不再是硬约束，则主轨可改回 Dify。
  4. 拿到 DIFY_API_KEY 跑通 head-to-head 后，若 Dify 定量通过率与 harness 持平且管控可接受，则本 ADR 结论从"不该用"降级为"可平替，按团队熟悉度选"。

9. 待核实清单（首次联调按实测校正，不当前置结论）

  • ✅ 已校正（streaming 暴露工具调用）：原假设"Dify 完全看不到工具调用"已推翻——chat-messages 的 Agent 应用只支持 streaming，且 streaming 的 agent_thought 事件携带 tool / tool_input / observation。论据二已据实测改写为"流式事件可见 vs durable span 树"。（[待核实: Dify 官方 API 文档] 仍建议核对各事件的完整 schema 与字段含义）
  • ✅ 已校正（无 mandatory 门控）：Dify Agent App 只支持 streaming，streaming 响应里没有 gate / confirmation 信号字段；门控纯靠提示词（踩坑4）。论据一从"advisory"坐实为"API 侧无强制门控信号"。
  • [待核实] Dify 日志页面"暂无日志"是"预览会话不写日志"还是"该版确实不落日志"——不影响会话级结论，但影响能否拿到持久化样本做离线分析。
  • ✅ 已确认（2026-10-05 控制台截图）：HRAH-Dify-Control 选用的模型为 DeepSeek V4.1 Flash（LLM / CHAT / 1000K 上下文，支持 VISION，无「不兼容」告警；搭建时 gpt-5.2 因不支持工具调用已切换）。注意这是 dify.ai 模型市场的显示名，其底层映射以平台为准；与 harness 侧官方 API 的 deepseek-chat 并非同一端点——D 类差异归因于"模型/端点 + 提示词"的证据更充分。
  • [待核实] shell_run 这类平台内置工具在 Agent 模式下的可调范围与开关项——本 ADR 仅实测到它会被自动调用，其完整清单与禁用方式以 Dify 官方文档为准。
