BUG-001 · 提示语污染了工具入参

  • 日期：2026-10-05
  • 发现方式：自己发现（跑 demo 场景 5 时看到输出异常）
  • 现象： 用户说"帮我查一下年假制度"，工具收到的 query 却是： '帮我查一下年假制度\n请只输出一个 JSON 对象。' 把写给模型看的提示语尾巴一起传进去了。功能能跑通，但数据在悄悄变脏。
  • 定位过程： 1. 确认输出异常 → 工具入参不对 2. 看 harness/llm.py 的 _decide()，发现 search_knowledge 分支写的是 {"query": u} 3. 追 u 的来源：_route() 从 【用户最新输入】 之后截取全部内容，包含 planner 拼的尾句
  • 原因： planner 组装 prompt 时在末尾追加了 请只输出一个 JSON 对象。， 而 Stub 的入参解析直接整段截取，没有剥离提示语。
  • 修复： python # harness/llm.py _decide() u = (user or "").split("请只输出一个 JSON 对象")[0].strip()
  • 教训： 模型看到的文本 ≠ 用户说的话。 两者必须在解析层显式分离。 这类问题不会报错、不会崩溃，只会让数据慢慢变脏——是最容易被忽略的一类 bug。 面试可讲："我调试时发现提示语污染了工具入参，功能是对的，但传进去的数据是脏的。"

BUG-002 · 共享 session 导致后续场景被短路

  • 日期：2026-10-05
  • 发现方式：协助调试发现（AI 跑 demo 时发现所有场景结果相同）
  • 现象： 4 个场景全部返回 done，场景 2/3/4 应该分别是追问、待确认，却都被判成"已完成"。
  • 定位过程： 1. 观察：只有第一个场景是真的执行了工具 2. 追 runner.run() → session.observations 是实例级共享的 3. Stub 的策略是"只要看到 【已执行步骤与结果】 就 FINISH" 4. 场景 1 执行后 observations 非空 → 场景 2/3/4 一进来就被 FINISH
  • 原因： demo 复用同一个 AgentRunner（同一个 session），上一轮的 observations 串到了下一轮。
  • 修复： python # demo.py：每个场景独立会话 for i, text in enumerate(SCENARIOS, 1): runner = AgentRunner(llm, registry, max_steps=6, auto_confirm=False)
  • 教训： 评测与演示必须保证用例之间状态隔离，否则指标全部失真。 这条后来会成为评测框架的一条硬约束：每条用例独立 runner。

BUG-003 · 关键词歧义导致意图误判

  • 日期：2026-10-05
  • 发现方式：协助调试发现（AI 跑 demo 时发现场景 3/4 路由错误）
  • 现象：
  • "给张三安排明天下午面试" → 没匹配上，走了兜底 FINISH
  • "发邮件通知候选人面试时间" → 被判成"安排面试"（因为含"面试时间"）
  • 定位过程： 1. 看 StubLLM._decide() 的分支顺序 2. schedule_interview 的关键词含"面试时间"，抢在邮件分支前面命中 3. "安排明天下午面试"不含连续的"安排面试"，所以匹配失败
  • 原因： 关键词设计太具体（要连续匹配）且分支顺序不合理。
  • 修复： python # 1. 邮件分支前置（含"邮件"优先判定） # 2. 安排面试改为组合判断，不再要求连续字符串 if "面试" in u and any(k in u for k in ("安排", "约", "预约", "定", "排期")):
  • 教训： 意图路由的分支顺序就是隐式优先级，必须显式设计并写注释说明为什么这么排。 真实场景里这应该用意图分类器 + 评测集来验证，而不是堆关键词。

BUG-004 · 关键词间隔表达导致工具漏选（M2 上下文管理阶段暴露）

  • 日期：2026-10-05
  • 发现方式：自己发现（跑 demo.py --context 时看到备注"无工具命中关键词"）
  • 现象： M2 上线后，场景 3「给张三安排明天下午面试」的上下文账本打出一条备注： 备注: 无工具命中关键词，仅注入得分最高的 1 个（模型应 FINISH 说明不支持） 注入工具: ['draft_email', 'schedule_interview', 'send_email'] 明明是要安排面试，schedule_interview 却是靠"高风险工具保护规则"兜底进去的， 不是靠意图匹配进去的。功能没坏，但意图筛选这一段实际是失效的。
  • 定位过程： 1. 看账本备注 → 一个工具都没命中 2. 查 tools/hr_tools.py 里 schedule_interview 的 keywords： ["安排面试", "约面试", "面试时间", "预约"] 3. 用户输入是「给张三安排明天下午面试」——"安排"和"面试"中间隔了 5 个字， 四个关键词没有一个能连续命中 4. 对比：Stub 之所以还能正确调工具，是因为 BUG-003 修过组合判断， 兜底逻辑掩盖了筛选逻辑的缺陷
  • 原因： 字面关键词匹配要求连续子串，对"动词 + 插入语 + 名词"这种自然语言表达天然不兼容。
  • 修复： python # tools/hr_tools.py schedule_interview: keywords=[..., "面试"] # 补一个宽口径词 generate_interview_plan: keywords=[..., "方案", "问题"] # 同时补特征词，避免被"面试"抢走 靠"命中数量打分"来区分：「安排…面试」只有 schedule 命中 1 次； 「生成面试方案」plan 命中 2 次（面试方案 + 方案）→ plan 胜出。
  • 教训（这条很值钱）： 1. 兜底逻辑会掩盖主逻辑的缺陷。如果不是 M2 把"注入了哪些工具、为什么" 显式打进账本，这个失效会一直躲在"反正功能是对的"后面。 → 这就是可观测性的直接收益：不是等它炸，而是让它主动告诉你哪里在退化。 2. 关键词匹配只是过渡方案。M4 接真模型时应换成 embedding 相似度， 并用评测集的"意图识别准确率"来量化换与不换的差别。 3. 面试可讲："我做完上下文预算之后，账本里一条备注暴露了意图筛选其实是失效的—— 这个 bug 之前一直被兜底逻辑盖住了。"

BUG-005 · 关键词过宽导致误注入无关工具（与 BUG-004 同根因的另一面）

  • 日期：2026-10-05
  • 发现方式：协助定位（用户复查 demo.py --context 账本后问"这个结果对吗"，核对时发现）
  • 现象： 场景 4「发邮件通知候选人面试时间」注入了 3 个工具： 注入工具: ['send_email', 'schedule_interview', 'get_candidate'] 其中 get_candidate（查候选人状态）跟"发面试通知"这件事毫无关系，属于误注入。
  • 定位过程： 1. 逐个核对被注入工具的关键词命中来源 2. get_candidate 的 keywords 含「候选人」——而用户句子里正好有"候选人"三个字 3. 同理 schedule_interview 的 keywords 含「面试」——"面试时间"也被它吃掉
  • 原因： BUG-004 修漏选时补进了「面试」「方案」「问题」这类宽口径词， 代价是误命中率上升。漏选和误选是同一根因的两面： 字面匹配没有语义，"候选人"既可能是查询意图，也可能只是句子的宾语。
  • 修复（M3 时的判断）： 当时只记录不改，计划 M4 换 embedding 相似度。
  • 实际修复（M4）： 没有换 embedding，改成了强弱信号加权打分 + 全局阈值（详见 docs/02-ADR-工具选择策略.md）： python # tools/hr_tools.py get_candidate keywords=["候选人", "状态", "查询"] # 弱信号 +1，单独命中不够 strong=["候选人状态", "候选人进度", "候选人情况", r"候选人.{0,6}?(状态|进展|进度|情况|资料|信息)"] # 强信号 +3 入选门槛设为 3 分：裸词「候选人」只得 1 分 → 不再被注入 → A05 转绿。
  • 为什么没换成 embedding（这是个取舍，不是偷懒）： 1. 引入向量会带来 Key / 依赖 / 延迟，而这条选择模型太轻，不值当 2. 更关键的：一旦用模型做工具选择，A 类指标就不再是"与模型无关"的引擎指标， 评测就从"测引擎"变成了"测模型"，指标体系的定义就散了 3. 加权规则可解释——命中的是哪个词、多少分，全在上下文账本里，出问题十秒定位
  • 教训： 1. 关键词加宽会同时降低漏选、抬高误选。这两个指标必须一起看， 只盯"有没有匹配上"，会把问题从一头推到另一头。 → 所以 M3 评测集必须同时包含两类用例：「该选却没选」和「不该选却选了」。 2. 这类问题只有把"注入了什么、为什么"显式打印才看得见——这是 M2 账本的第二次收益。

小坑 · Python 字符串里写中文引号导致 SyntaxError

  • 日期：2026-10-05
  • 发现方式：自己发现（跑 scripts/context_benchmark.py 报错）
  • 现象： File "scripts/context_benchmark.py", line 194 "- 历史分区与"本轮执行结果"共享额度，执行结果优先（它是当前决策的直接依据）。", SyntaxError: invalid syntax. Perhaps you forgot a comma?

BUG-006 · 基准测试的基线调用了当前实现，度量会随代码一起漂移

  • 日期：2026-10-05

  • 现象： context_benchmark.py 里代表"旧做法"的那一栏是这么写的： python def m1_measure(registry, user_input, history): specs = registry.select_for_intent(user_input, top_k=5) # ← 调的是当前实现 它调用了当前代码的 select_for_intent。 M4 一旦改优化这个函数，所谓"基线"也跟着变瘦了—— 对比就变成了跟一个不断变化的影子比，降幅会被动缩水。

  • 教训（这条我给满分）： 1. 度量 Kill 自己的最好方式，就是让基线依赖被测代码。 写优化类脚本时，基线要像"标本"一样被冻结，而不是让活着。 2. 这类 bug 不会报错、不会崩，只是数字悄悄失真——是最阴的一类。 3. 面试可讲："我给这个项目做基准测试时踩过一个坑——基线调用了当前实现， 等于跟自己的影子比。后来把旧规则���算出来冻结住，才发现真实收益比原先报的大不少。"

BUG-007 · 参数名 type 遮蔽内置 type，导致异常处理块二次崩溃（M4 接真模型暴露）

  • 日期：2026-10-05
  • 发现方式：协助调试发现（AI 跑 live 评测时，24 条 × 3 轮里有 14 轮崩在 tracer 的 except 块）
  • 现象： live 评测里每遇到一次 DeepSeek 偶发 SSL EOF，就跟着抛： TypeError: 'str' object is not callable 栈顶在 harness/tracer.py 的 span() 上下文管理器 except 块，整轮评测被判失败。 真正导致失败的网络错误被这个 TypeError 盖住了，一眼看不出根因。
  • 定位过程： 1. 看 reports/debug_traceback.txt，栈顶在 tracer.py 第 123 行 self.end_span(sp, status="failed", error=f"{type(e).__name__}: {e}") 2. 这行本意是取异常类型名（如 URLError），但 type 在这里指向的是字符串参数，不是内置 type 3. 往上查：start_span(self, type: str, ...) 和 span(self, type: str, ...) 把参数命名为 type，遮蔽了内置 type 4. 所以 except 里调 type(e) 实际是在调那个字符串 → 字符串不可调用 → 二次异常
  • 原因： 方法参数名叫 type，遮蔽了内置 type。这错平时完全没事—— 只有当「主逻辑先抛异常」时（这里就是 SSL EOF），except 块里的 type(e) 才会触发二次崩溃。 典型的「只在真网络 / 生产下才暴露」的 bug，Stub 永远触发不了。
  • 修复： python # harness/tracer.py def start_span(self, span_type: str, name: str, ...) -> Span: # type → span_type def span(self, span_type: str, name: str, ...) -> Iterator[Span]: # 同上 # except 块里的 type(e) 自动恢复指向内置 type
  • 教训（这条很值钱）： 1. 永远别用 type / id / list / dir 这种内置名当变量名，哪怕只是个方法参数。 IDE 不报错、单测不触发，运行时才炸。 2. 异常处理的 except 块本身也可能抛异常。上下文管理器里 except Exception: ...; raise 的兜底， 绝不能自己再崩——否则会掩盖真正的根因（这里是 SSL EOF，被 TypeError 盖住了）。 3. 这条 bug 的触发条件是「先有另一个异常」，所以它是只在生产环境才暴露的一类 bug。 写引擎层代码时，span/日志这类"兜底路径"要当成产品代码一样测，不能假设它永远走不到。

BUG-008 · 对外 HTTP 调用没有重试，瞬断直接变成致命错误（M4 接真模型暴露）

  • 日期：2026-10-05
  • 发现方式：协助调试发现（live 评测 14 轮因 SSL EOF 崩溃，与 BUG-007 同源）
  • 现象： DeepSeekLLM.complete 调用接口偶发 ssl.SSLEOFError: UNEXPECTED_EOF_WHILE_READING， 直接抛出未捕获异常，整轮评测失败。一次瞬断就把一条用例判死。
  • 定位过程： 1. 看 traceback：urllib.request.urlopen 在读取响应时 SSL 连接被对端重置 2. 当时 complete 只有单次 urlopen，没有重试逻辑 3. 对照 C4 健壮性硬约束：任何对外 HTTP 调用必须有「超时 + 重试 + 降级」
  • 原因： 对外网络调用只有一次尝试。瞬断、限流（429）、5xx、对端重启都是常态， 当成致命错误直接上抛，等于把"概率性抖动"放大成"确定性失败"。
  • 修复： python # harness/llm.py DeepSeekLLM.complete for attempt in range(3): try: with urllib.request.urlopen(req, timeout=self.timeout) as resp: body = json.loads(resp.read().decode("utf-8")) break except urllib.error.HTTPError as e: if attempt < 2 and e.code in (429, 500, 502, 503, 504): time.sleep(0.5 * (2 ** attempt) + random.uniform(0, 0.3)) # 指数退避 + 抖动 continue raise RuntimeError(f"DeepSeek 调用失败 {e.code}: {detail}") from e except urllib.error.URLError as e: if attempt < 2: time.sleep(0.5 * (2 ** attempt) + random.uniform(0, 0.3)) continue raise RuntimeError(f"DeepSeek 网络错误: {e.reason}") from e 只对可重试错误重试（429 / 5xx / 网络层 URLError）；4xx 是请求本身有误，重试没用，直接报错。
  • 教训： 1. 任何对外网络调用都不能只有一次尝试。瞬断、限流、对端重启是常态不是异常。 2. 重试要区分「可重试 / 不可重试」：4xx（请求错了）重试纯浪费；5xx / 429 / 网络层错误才值得重试。 3. 退避必须加抖动，否则一批请求同时重试会把对端打进"重试风暴"（惊群）。 4. 这条和 BUG-007 是同一轮 live 评测一起暴露的：Stub 永远走不到网络路径， 接真模型 = 把"只在生产才暴露"的一类缺陷提前到开发期发现。这正是 M4 接真模型的最大收益之一。

踩坑7 · Cloudflare 按 User-Agent 封禁 urllib，Dify 云端调用吃 403（M5 联调暴露）

  • 日期：2026-10-05
  • 发现方式：自己发现（跑 scripts/_dify_probe.py / run_dify_eval.py 时收到 403 + error code: 1010）
  • 现象： 用 urllib.request 直连 https://api.dify.ai/v1/chat-messages，返回 HTTP 403，响应头 Server: cloudflare、cfOrigin;dur=0，正文 error code: 1010。 cfOrigin;dur=0 的含义是请求根本没到达 Dify 源站，被 Cloudflare 边缘拦了。
  • 定位过程： 1. 用 curl -i 复现同样的 403，确认不是 Python 代码问题，是网络层 2. 对比：浏览器能正常打开 dify.ai → 怀疑是 UA 指纹 3. 看 urllib 默认 UA 是 Python-urllib/3.x——典型的 bot 特征 4. 加 User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) HRAH-Eval/1.0 重试 → 响应头变 cfOrigin;dur=141、X-Version: 1.17.1，说明已到达源站（下一步才暴露 踩坑8 的 400）
  • 原因： api.dify.ai 前置 Cloudflare，对默认 Python UA 启用 bot 防护，直接 403。
  • 修复： python # evals/dify_adapter.py DifyClient.__init__ self.user_agent = "Mozilla/5.0 (Windows NT 10.0; Win64; x64) HRAH-Eval/1.0" # chat() 的 headers 里带 "User-Agent": self.user_agent, "Accept": "text/event-stream"
  • 教训： 1. 直连第三方 API 时，UA 不是装饰——很多站（尤其套了 Cloudflare 的）会对默认 脚本 UA 做 bot 拦截。报错 403 先怀疑 UA，再怀疑 key。 2. cfOrigin;dur=0 是个好信号：它告诉你"没到源站"，问题在边缘/CDN，不在你的 key 或代码。 3. 面试可讲："我联调 Dify 云端时被 Cloudflare 按 UA 拦了 403，看 cfOrigin;dur=0 判断是边缘没放行，换浏览器 UA 就到了——这类排错比写功能更见功力。"

踩坑8 · Dify Agent 应用只支持 streaming，blocking 被 400 拒（M5 联调暴露）

  • 日期：2026-10-05
  • 发现方式：自己发现（踩坑7 修好后，请求到达源站立刻返回 400）
  • 现象： 修好 UA 后，Dify 返回 HTTP 400，正文： {"code": "streaming_not_supported", "message": "Agent App only supports streaming response mode", ...}
  • 定位过程： 1. 踩坑7 之后请求已到源站（X-Version 正常），所以这是 Dify 的业务校验错误，不是网络 2. 看报错：Agent App only supports streaming response mode——明确说 Agent 类应用不支持 blocking 3. 把 response_mode 从 "blocking" 改成 "streaming"，并补 SSE 解析
  • 原因： Dify 的 Agent 类型应用（区别于普通 Chatbot）强制 streaming，blocking 模式不被接受。 早期适配器按 Chatbot 的 blocking 模式写，所以一改 UA 就暴露这个 400。
  • 修复： python # evals/dify_adapter.py chat() payload["response_mode"] = "streaming" # 新增 _read_stream(resp)：逐行解析 SSE，从 message/agent_message 拼 answer， # 从 agent_thought 抽 tool/tool_input/observation，遇 [DONE] 结束
  • 教训： 1. Dify 不同应用类型的 API 约束不一样：Chatbot 支持 blocking/streaming，Agent 只支持 streaming。 接第三方 API 前先看官方文档的应用类型差异，别套用直觉。 2. streaming 反而是更优解：agent_thought 事件在流式里才带工具调用明细， 这反而让我们拿到了"Dify 调了哪个工具"的证据（见 ADR-003 论据二校正）。 3. 面试可讲："我把 Dify Agent 的 blocking 改 streaming，顺手发现流式响应里 agent_thought 暴露了工具调用——本来以为 Dify 完全黑盒，实测后校正了结论。"
