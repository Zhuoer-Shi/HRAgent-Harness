Dify vs HRAH 横向对比报告

配套文档：docs/03-ADR-什么时候不该用Dify.md（决策落点）。 本报告把两条轨道的逐条结果并排，给评审看清楚"差异到底在哪、为什么"，并明确标注哪些能比、哪些不能比。

0. 数据来源与口径（先看这个，避免误读）

  • 数据来源
  • 自研 harness 主轨：reports/eval_latest.json（backend=deepseek，repeat=3，生成于 M4 live 评测，见 README.md M4 节）
  • Dify 对照轨：reports/dify_eval_latest.json（repeat=1，2026-10-05 用有效 DIFY_API_KEY 实跑）
  • 三桶口径（贯穿全文，绝不把"不可比"算成"失败"）
  • 通过：可比维度 + 同一套裁判（规则 / LLM 多数表决）判定合格
  • 未判定：Dify 调用失败或 LLM 裁判不可用（如缺 DEEPSEEK_API_KEY）。本次 0 条
  • 不可比（设计）：用例依赖 Dify 不建模的信号（工具清单 / 门控 / 状态机 / 副作用 / 引擎内部单元）。不计入通过率。本次 Dify 侧 16 条
  • 重复次数不一致（诚实标注）：harness 主轨 ×3（含稳定性指标），Dify 对照轨 ×1（适配器逐条一次性调用，未测稳定性）。所以 Dify 侧的"通过"只代表一次性结果，两边稳定性不可直接比较。
  • Dify 生成模型（已确认）：Dify 应用 HRAH-Dify-Control 实际选用 DeepSeek V4.1 Flash（2026-10-05 控制台截图确认；卡片标签 LLM / CHAT / 1000K 上下文 / 多模态 VISION）。切换该模型后工具调用不兼容告警消失 → 判定支持 Function Calling。这直接影响 D 类内容质量的可比性解读——见 §2.4。

1. 总览对照

维度 自研 harness（主轨） Dify 对照轨
重复次数 ×3 ×1
执行用例 24 24（其中 16 条"设计不可比"、未联网）
可比用例数 24（全可比） 8（B05/B06 + D01–D06）

2. 逐类对照

2.1 A 类 · 意图与工具选择（6 条）

  • harness：6/6 —— 断言"上下文注入了哪些工具"（tools_selected_include/exclude），不依赖模型，换模型仍可比。
  • Dify：6/6 不可比 —— 依赖 tools_selected_include/exclude，Dify 不暴露规划器候选清单，无对应内部 API。
  • 解读：工具选择是 harness 引擎职责，A 类测"注入哪些工具"而非"最终调哪个工具"。Dify 侧天然不可比属设计使然。

2.2 B 类 · 条件缺口与追问（6 条）

  • harness：6/6
  • Dify：B01–B04 不可比 + B05/B06 可比
  • B01–B04 依赖 awaiting_input 状态机，Dify 不建模 awaiting_*，归一化 status 恒为 done。
  • B05 ✅ 双方通过（知识缺口下明确说"资料不足"，不编造）
  • B06 ✅ 双方通过（用户中途取消，正常收尾不卡死）
  • 诚实注：B06 在 Dify 侧因 status 恒为 done 而平凡满足，有效信号其实只有 B05；harness 侧 B06 是真状态机转移（S_AWAITING_INPUT → 取消收尾）。

2.3 C 类 · 门控与契约（6 条）

  • harness：6/6 —— mandatory 门控：确认前零副作用（no_side_effect）、契约拦住非法工具名 / 缺必填参（C05/C06）、确认后才落地（confirm_then_side_effect）。
  • Dify：6/6 不可比 —— 依赖 gate_count / no_side_effect / confirm_then_side_effect / pending_tool / 引擎内部单元断言。
  • 解读：C 类是 harness "受控"二字的落点，也是 Dify advisory 管控的盲区。不可比是架构差异，不是 Dify 业务失败。

4. 关键结论与误读防范

  1. "Dify 通过率 87.5% 不输 harness" —— 误读。 Dify 的 87.5% 建立在"砍掉 16 条控制面用例"的前提下。把这 16 条加回（harness 全过），harness 才是覆盖完整可控性定义的那个。
  2. "Dify 内容质量更高所以引擎更好" —— 误读。 D 类差的是模型 / 提示词，且 Dify 用模型未知；要公平比内容质量应锁定同一生成模型重跑。
  3. "harness 88% 说明有 12% 不可控" —— 误读。 3 条失败全是 MODEL-QUALITY（DeepSeek 写得太浅），不是控制失效；A/B/C 类（控制面）相关 18 条全过，门控 / 契约 / Trace 硬指标 100%。
  4. 真正引擎级可比、且能区分两条轨道的，只有 B05/B06 + D 类这 8 条；其余 16 条是"Dify 架构上就不提供这些信号"的证据，不是比赛分数。

5. 限制与待核实

  • ~~Dify 应用后台生成模型名称~~ ✅ 已确认：DeepSeek V4.1 Flash（2026-10-05 控制台截图；与 harness 官方 deepseek-chat 非同一端点）。
  • [待核实] Dify 日志页是否落 span 级数据（影响能否离线回放定位）。
  • Dify 对照轨未接知识库，B05 考的是模型"不编造"而非检索，与 harness（接 mock KB）非完全同构。
  • Dify 侧 repeat=1，缺稳定性数据；如需与 harness ×3 对齐，重跑 python scripts/run_dify_eval.py --repeat 3（需 DIFY_API_KEY + DEEPSEEK_API_KEY + Dify 云端额度）。
  • 诚实红线：以上均为离线固定用例集结果，非上线数据；本项目未上生产、无真实用户流量。

6. 一句话总结

Dify 是"快上线"的默认解，低风险内容生成它更快更好；当出现"不可逆动作 + 必须拦得住 + 出事要能定位到那一步"时，自研受控 harness 才值回票价。本对比用 16/24 条"设计不可比"如实证明了这道分界线在哪，而不是把不可比硬凑成胜负。
