Prompt 迭代记录

一句话：这次"迭代"最有价值的结论是——改 prompt 之前必须先归因。我本来想通过改 prompt 提升 D 类内容质量，归因后发现三条失败没有一个能用 prompt 修好。

0. 这份记录回答什么

AI 产品作品集里，「Prompt 迭代过程」是最能证明动手能力的一块。但它的价值不在于"我改了三次提示词"，而在于我能不能说清：为什么改、改了哪一层、改完有没有真的变好。

这份记录如实复盘一次真实的迭代，包括一个不光彩但重要的部分：我的第一反应是错的，靠看 span 树才纠正过来。

1. V1：当前的系统提示词

harness/planner.py 里的 SYSTEM_PROMPT（V1）：

你是一个受控 Agent 的规划器。你只能从固定的动作空间中选一个动作。

【动作空间】
1. CALL_TOOL       —— 调用一个已注册的工具
2. ASK_USER        —— 信息不足，向用户追问（一次只问最关键的 1~2 项）
3. REQUEST_CONFIRM —— 动作高风险，请求人工确认
4. FINISH          —— 任务完成，给出最终回答

【输出格式】只输出一个 JSON 对象，不要输出任何其他文字：
CALL_TOOL:        {"action":"CALL_TOOL","tool":"工具名","args":{...},"reason":"..."}
ASK_USER:         {"action":"ASK_USER","question":"...","missing":["字段名"],"reason":"..."}
REQUEST_CONFIRM:  {"action":"REQUEST_CONFIRM","tool":"工具名","args":{...},"reason":"..."}
FINISH:           {"action":"FINISH","answer":"...","reason":"..."}

【硬性约束】
- 只能使用工具清单中列出的工具名，绝不臆造工具。
- 缺少必要信息时用 ASK_USER，不要靠猜测填参数。
- 需要调用清单以外的能力时，直接 FINISH 并说明不支持。

V1 的定位：它只做一件事——约束动作空间（选哪个动作、哪个工具、哪些参数）。它刻意不指导内容质量，因为当时的设计假设是"内容质量是工具返回数据的事，不是 prompt 的事"。

2. 迭代触发：D 类 3 条失败

接 DeepSeek 真模型跑全套 24 条 × 3 轮，D 类 6 条里 3 条失败：

用例 输入 期望 结果
D03 帮我准备 Java 岗的面试问题 面试方案含 ≥3 个考察维度 ❌
D04 给张三写一封面试通知邮件 邮件草稿语气正式、含时间与岗位 ❌
D05 帮我给这份简历打个分 评分 + 理由 ❌

D01/D02/D06 通过。3 条失败看起来都是"内容质量"问题——所以我的第一反应自然是：

"DeepSeek 内容生成太浅了，改改 prompt，让它把回答写详细点。"

（这个判断当时还写进了 cases.py，标注 known_issue="MODEL-QUALITY"。）

3. 先归因：看 span 树，别急着改

在动手改 prompt 前，我先把这 3 条失败的 span 树捞出来看。结果推翻了我的假设：

D03（面试方案）——模型在追问姓名，不是内容浅

[plan] plan[0] ASK_USER
  input : 生成面试方案需要候选人姓名和岗位名称，目前缺少候选人姓名。
  output: 请问候选人的姓名是什么？

模型没有生成内容，而是先追问"候选人姓名"。原因：generate_interview_plan 把 candidate 设成了必填参数。但"准备某岗位的面试问题"本质是按岗位生成题库，不需要具体候选人。是工具契约错了，不是 prompt 错了。

D04（邮件）——注入 0 个工具，模型无从下手

[plan] context.build  输出: 注入 0 个工具
[plan] plan[0] FINISH 输出: 当前没有可用的工具（如邮件发送、模板生成等）……

"写一封面试通知邮件"没命中 send_email（强信号是"发/发送邮件"）也没命中 draft_email（强信号是"起草/拟邮件"），于是上下文注入 0 个工具，模型只能拒绝。是工具选择漏匹配，不是 prompt 错。

D05（简历评分）——模型在追问 JD 和姓名，这是对的

[plan] plan[0] ASK_USER
  output: 请提供候选人姓名和对应的 JD（职位描述或标题），我才能为这份简历打分。

screen_resume 需要 candidate + jd，用户"给这份简历打个分"两个都没给。模型追问是唯一正确的行为——但 rubric 却期待一份完整评分。是测试用例输入不足，不是 prompt 错。

4. 归因结论：三条失败都不是 prompt 问题

用例 真实根因 类别 该改的层
D03 generate_interview_plan 把 candidate 误设为必填 工具契约缺陷 工具契约，不是 prompt
D04 "写…邮件"未命中任何邮件工具，注入 0 工具 工具选择缺陷 工具信号，不是 prompt
D05 用例输入缺 candidate+jd，正确行为就是追问 测试设计缺陷 测试用例，不是 prompt

更深一层的反思：我连失败归因都做错过一次——把三条"工具/测试缺陷"误归为"模型内容质量差"（MODEL-QUALITY）。这本身就是失败模式手册里"度量评测缺陷"的活例子：归因也要被归因。

cases.py 里这三条的 known_issue 已从 MODEL-QUALITY 修正为 CONTRACT-001 / SELECTION-001 / CASE-001，并保留原文作为"我犯过这个错"的证据。

5. 改对层：D04 工具选择修复（真实前后对比）

prompt 改不动 D04，因为问题在"意图 → 工具"的映射。修复落在 tools/hr_tools.py，给 draft_email 补上"写…邮件/通知"的间隔正则：

strong: [..., r"写.{0,8}?邮件", r"写.{0,8}?通知"]

修复后用同一输入验证工具选择：

输入 修复前注入 修复后注入
给张三写一封面试通知邮件 （0 个工具）→ FINISH 拒绝 draft_email（得分 6）

顺带验证了 D03/D05 的工具选择本来就对（分别正确选中 generate_interview_plan、screen_resume）——进一步坐实：它们卡在契约和测试设计，不在选择、更不在 prompt。

诚实声明：这次修复解决的是 D04 的第一步（工具能选上了）。D04 后续仍可能追问"面试时间"，因为 draft_email 的 subject/body 也必填、而用户没给——这又是"契约过严 / 输入不足"问题，与 prompt 无关。所以 D04 若要彻底转绿，需继续修契约或用例，而不是改 prompt。

6. 那 prompt 到底该不该改？

该改，但要改对地方。这次迭代的真实教训是：

  • prompt 该管的是动作选择时的语义约束——"缺信息要追问、不要瞎猜参数、不要臆造工具"。这是 V1 已经在做的，且做得对（三条失败里模型的追问、拒绝都符合约束，恰恰说明 prompt 没坏）。
  • prompt 管不了的是内容质量——因为本项目的产出内容由 mock 工具返回固定数据，内容上限被 mock 数据锁死，改 prompt 也改不动"mock 只返回 2 条面试问题"这个事实。

换句话说：在这个 mock 工具架构下，"通过改 prompt 提升内容质量"是个伪命题——内容质量的上限在工具返回值，不在 prompt。要真正迭代内容质量，得先让工具返回更丰富的数据（或接真实生成），那时 prompt 的"交付规范"（FINISH 时要交付完整可用的结果、不要只说"已完成"）才有用武之地。

这条结论，比"我改了三次 prompt"更能证明我理解 Agent 内容质量的边界在哪。

7. 方法论：Prompt 迭代三步法

这次迭代沉淀成一条可复用的动作序列：

  1. 先归因，再决定改哪一层。失败有引擎 / 模型 / 度量 / 环境四层（见 docs/05-失败模式手册.md），先看 span 树定位到具体层。改一个没问题的层是最贵的错。
  2. 能改规则层就改规则层。工具信号、参数契约、断言条件这些是确定性的，改了就能验证，且不会引入模型波动。
  3. prompt 只改"语义约束"，不试图靠它"背"内容。内容质量靠工具数据 + 交付规范，不靠把 prompt 写得又长又满。

8. 关键洞察

  • 被问"你的 prompt 是怎么迭代的"：别只说"改了三次"，讲"我先归因，发现三条失败都不是 prompt 问题，于是改了对的层"——这才是真实且有判断力的答案。
  • 被问"为什么不用更好的 prompt 让 D 类通过"：答"因为 D 类失败根因是工具契约/选择/测试设计，改 prompt 是改错层；而且 mock 工具下内容上限被数据锁死，prompt 改不动"。
  • 被问"你自己归因错过吗"：诚实答"错过，我把三条工具/测试缺陷误标成了模型内容质量，靠看 span 树才纠正"。归因也会错，能自我纠正比从不犯错更有说服力。
